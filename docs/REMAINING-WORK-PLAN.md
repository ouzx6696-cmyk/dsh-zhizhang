## 5. S0：CI、候选构建和证据补齐

### 5.1 解决 CI 状态不可确认

1. 重新读取远端 `master`，记录完整 SHA、工作区状态和操作时间。
2. 通过 GitHub 网页或已获授权的工具查询该 SHA 的 Actions；没有权限时由维护者在网页导出运行链接、结论和日志。
3. 诊断 `Forbidden` 是平台网络限制、令牌权限还是仓库权限；只根据安全元数据判断，不在聊天或日志输出凭据，不擅自扩大权限。
4. 区分 `success`、`failure`、`cancelled`、`skipped`、`queued`。被取消或跳过的必需 job 不算通过；旧提交的绿灯不能替代当前提交。
5. 失败先归类：业务回归、Windows 路径/换行、下载故障、打包故障或权限问题。修复代码后重新验证；只对明确的基础设施瞬断做有限重试，不无限重跑掩盖失败。

**验收：** 当前候选 SHA 的 Linux 核心、Windows 核心、桌面运行时、GUI 结果均可定位到具体运行记录。

### 5.2 普通推送不会完成打包验收

当前 `ci.yml` 中，普通分支推送主要跑检查和桌面测试；`scope` 仅在手动触发或标签上下文将 `package` 设为真。因此普通推送成功，不能说明 NSIS/ZIP、随包 Python 或更新文件已经验过。

候选提交推送后，维护者或已获授权的执行者手动运行 **`ci.yml`**，开启当前配置下的打包路径，并收集 `writer-windows-packages`。使用运行记录中的 `head_sha` 确认构建的是预期候选。

示例命令仅供具备权限者执行，不是本次文档任务已经执行的动作：

```bash
gh run list --repo ouzx6696-cmyk/dsh-zhizhang --commit <候选完整SHA>
gh workflow run ci.yml --repo ouzx6696-cmyk/dsh-zhizhang --ref master
```

手动触发前核对分支提交，触发后核对 run 的 SHA；如果运行期间 master 又有改动，不能靠分支名判断产物归属。

**不要用创建临时 `v*` 标签来测试打包。** 当前 `release.yml` 会响应此类标签并进入发布流程；正式授权前也不要手动触发 `release.yml`。

### 6.2 重要的测试工具兼容问题

当前包体启动检查使用 Playwright `electron.launch` 并访问主进程。关闭 Node inspect 后，这条连接路径可能失效，不能为了让测试连接而把正式包的 Inspect fuse 重新打开。

建议：

1. 开发版继续使用现有 Electron Playwright 测试。
2. 正式包检查器原生启动安装后的 EXE，用仅绑定环回地址的 Chromium 调试连接检查渲染窗口及已有状态接口；或使用已经验证可行的其他不依赖 Node inspect 的方式。
3. 不新增测试专用生产 IPC；从实际安装包、app.asar、现有界面版本与行为取得证据。
4. 为 `NODE_OPTIONS` 注入准备一个只会在临时目录写标记的测试脚本；健康启动后标记必须不存在。
5. 给 Node `--inspect` 指定启动前确认空闲的端口；健康启动后该端口必须未监听。先确认应用正常启动，不能把“整个程序没启动”当作 Fuses 安全通过。
6. 启动正式 EXE 时不要依赖 `WRITER_USER_DATA` 隔离：当前入口只在非打包态采用它。使用独立 Windows 账户/可恢复测试系统，或先验证有效的隔离方式。
7. 验收结束关闭测试端口和进程，保留报告，不把调试配置写入生产默认值。

## 7. S1：交接遗留偏差的闭环方案

“交接中提到过”不等于当前一定存在产品缺陷。每项先用当前主线复现，再决定修复、保留或延期；已经解决的只补证据，不重复开发。

| 编号 | 需要核实的事项 | 实施与验证办法 | 放行标准 |
| --- | --- | --- | --- |
| D01 | 只读检查依赖当前选择的 `state.access`，跨项目实际目标未充分覆盖 | 从 A 项目发往 B 的请求，覆盖 root/base/work、长篇/头条、直接 IPC 与模型工具。分别让 B 被另一进程持锁，或 A 只读而 B 可写。若发现绕过，统一解析实际目标后复用现有写权限检查，不另写锁系统 | 被锁的实际目标绝不能被修改；普通可写目标不被错误拦截。若证实绕过，修复后才能发布 |
| D02 | 服务商分类结果尚缺明确诊断日志 | 在唯一分类边界记录 kind、状态码、阶段、attempt、reason 和已计费用量；复用现有 Diagnostics 脱敏，不记录请求原文、密钥或完整来源 | 一次失败能解释为何重试/暂停/失败；记录不泄露凭据 |
| D03 | 裸 ECONNRESET、ETIMEDOUT、Google 429 等边界 | 补脱敏真实报文夹具及 SDK 类型夹具，走实际分类与重试路径。保持 401/403 优先、欠费窄词、确定性参数错误不重试；不扩大到任意 quota/billing 字符串 | 同一错误只有一个分类结果；普通 429 不误作余额不足；是否拓展裸网络错误重试由维护者决定 |
| D04 | `timeoutMs` 和 stderr 64 KiB 范围 | 子进程在边界前/后完成、忽略 SIGTERM、输出恰好达到和超过上限、取消与超时竞争均实测；stderr/stdout 按字节计算，测试 UTF-8 多字节 | 必定收尾；超限/超时/取消错误可区分；有用计费和错误不丢失；不能静默截断当成功 |
| D05 | 编辑器未自动聚焦、Esc 由不同容器处理 | 键盘及鼠标打开编辑器，分别在正文、工具栏、弹窗和外壳按 Esc；覆盖长按和输入法组合。先保留已有行为，除非明确决定自动聚焦 | 一次 Esc 不直接丢脏稿，不误停任务；确认取消后焦点和正文保留 |
| D06 | 恢复旧版本草稿后只能冲突拒绝、清理“其他作品”的范围、迁移失败仅控制台记录 | 用旧版真实 localStorage 样本升级；磁盘正文变化后恢复草稿，再保存。验证新旧键冲突取舍、空间不足、失败后旧数据保留及不同文章的清理范围 | 不覆盖新正文、不误清当前稿；迁移失败不能丢唯一副本。合并/强制覆盖是新能力，未批准不补做 |
| D07 | 10 条提示在窄窗口是否遮挡写作区 | 760×650 与常用桌面尺寸、100/125/150/200% 缩放、明暗主题、鼠标悬停和键盘聚焦分别目视核对 | 提示可读可关闭，关键确认按钮和编辑操作可达；若实际遮挡则针对布局修复 |
| D08 | 新任务覆盖确认存在应用内与 host.confirm 两条路径 | 面板正常路径、状态过期、模型工具、连续点击、取消与切换作品均测试 | 未确认不覆盖恢复指针；取消后旧任务仍可恢复；无重复弹窗或确认串入其他作品 |
| D09 | FQ-19 放宽的是修订影响而非全部 changed 判定 | 从只有章纲到首次正文，再作第二次正文修改，核对 revision、历史、revisionImpacts、下游状态和快照 | 首次落稿不制造旧稿修订影响，真正修订仍保护历史；不用大范围放宽 changed 掩盖问题 |
| D10 | 活实例也显示“接管”、恢复错误码与旧方案不完全一致 | 活进程、死进程、异机名、损坏锁、确认期间换 ownerId 分别验证；保留实际存活提示和确认 | 活锁不自动删除，owner 改变时拒绝接管；错误码有测试和文档，不为追求字面一致重写全域码 |
| D11 | Windows 并发测试偶发失败与计时粒度 | 在 Windows 重复执行相关并发、思考看门狗用例，使用受控同步信号/假时钟验证行为，记录失败率及环境 | 真问题修产品；测试竞态修测试。不降低阈值、不跳过失败用例“保绿” |
| D12 | Python 3.8/3.9 只有注解结构证明 | 按第 9 节用真解释器跑桥和现有业务夹具；若不支持，明确修复兼容或申请调整开发支持范围 | 不以 AST 检查代替运行时兼容结论 |

D02–D04 以已暴露的错误诊断与契约为范围，不增加全新的监控系统。D05–D08 如仅是产品体验取舍，记录决定后延期，不把未授权新功能塞入补丁版。

已经合入的扁平 `record.reason`、CSV 转义、`INVALID_ARGS`、Python 环境变量提示及 `font-src 'self' data:` 应按当前行为保留并测试；不要仅为贴合旧文档改回另一套实现。

- 运行两种模式各自 `skill/tests/test_*.py`，以及已有能在该解释器执行的业务夹具；单独记录测试工具本身对 Python 版本的要求。
- 对 GBK 台账验证明确 UTF-8 提示且原文件未改；对 BOM、中文和生僻字验证单个 JSON 输出。
- 调用不存在的显式 Python 路径须直接失败；没有显式设置时才自动探测。
- 不使用 `from __future__ import annotations` 绕过原计划中已知测试兼容问题。

## 10. S3：真实模型测试与预算控制

### 10.1 先批准预算，后发生请求

维护者此前账户余额有限；未批准前不连接真实付费模型、不充值、不把连接测试当作免费操作。所有限流、余额、鉴权和恶意输入故障先用假模型模拟。

预算单必须包含：服务商、模型精确 ID、推理档位、经济档、两条任务内容、单任务及总费用上限、价格来源、允许的重试次数，以及超出估算时由谁决定停止。

注意：经济档“一章/一篇”也包含方法卡、规划、起稿、审读、事实链及可能的重试，**不等于只调用一次模型**。先盘点调用路径，保守估算输入、输出、缓存和重试成本，再确定额度。

客户端 token 预算不能当作严格的金额闸门。优先使用服务商能够实际执行的项目/密钥消费限额；没有该能力时，采用单任务串行执行、阶段边界人工核对、保守预留和明确停止条件，并披露无法保证精确金额硬上限。

### 10.2 两条必测业务路径

**RM01：经济档番茄一章。**

- 使用受控设定、已有章纲与适量正文，避免第一次测试就创建整本书。
- 执行起稿、择优/审读、修订、交付、作者采用、定稿与记账。
- 核对方法卡不含其他作品数据，阶段与终稿对应，硬伤有定位，暂停后进度仍在。
- 作者可评价文本可用性，但不以模型互评结果代替作者决定，也不宣称一次样本证明质量提升。

**RM02：经济档头条一篇。**

- 优先用已核对的作者素材，减少网络来源变化干扰；先跑卡片、标题、起稿，再跑事实链及现有 QA。
- 核对来源数字、引语、故事演绎标签和终稿事实链；实际采用失败须保留原卡片与标题。
- 记账后复检，核对没有不合理的自身比较；未实施 T134 时明确记录剩余规则边界。

已有真实任务中自然出现的长思考或可恢复暂停可以形成证据，但不为制造这些场景额外烧费。授权包含扩展推理档时再专项测试；否则仍使用看门狗模拟回归证明机制。

### 10.3 记录与停止条件

每条报告至少记录：

| 字段 | 要求 |
| --- | --- |
| 身份 | 源码 SHA、客户端/规则版本、服务商、模型、档位 |
| 任务 | 输入摘要、受控素材编号、是否冷方法卡/暖方法卡 |
| 时序 | 开始/结束时间、各阶段耗时、总墙钟时间 |
| 用量 | input、output、cacheRead、cacheWrite、各次 attempt；未知字段写未知 |
| 费用 | 客户端估算、服务商账单及币种；两者偏差和价格来源 |
| 结果 | 是否交付、是否通过 QA、作者是否采用、开放问题、暂停/失败原因 |
| 可恢复性 | 取消/重启后的状态、是否重复请求或重复交付 |

触达额度、报价无法确认、连续服务异常、出现数据保护问题或未经批准的新调用路径时停止。报告中保留失败和已计费用量，不删除失败记录制造“全程顺利”。

“未返回 cacheRead”不等于缓存未命中；“第二次较快”不等于命中率提升。需要收益对比时使用相同素材、模型、档位和缓存状态，单独批准额外成本后再测，不把本地算法基准换算成真实账单节省百分比。

结果写入 CHANGELOG 的“实测”说明，并保留脱敏原始记录。未执行或被停止的项目保持未完成；若维护者正式调整发布门槛，记录调整理由，不能默默省略。

实施顺序：

1. 用当前规则固化现有正例、反例及错误结果，取得基线。
2. 只修改已批准的词表/规则点，不改变 34/84/两轮等阈值，不借此重写方法原文。
3. 新增精确正反例，覆盖普通报道、引用他人声明、短数字、长文无小标题、自身台账、旧 QA 版本等。
4. 跑全部 Python 与 Node 业务用例、桌面两种模式和作者采用路径。已有过线夹具如改变结果，必须逐条解释，不调整夹具来掩盖误杀。
5. 核对旧 QA 可见但不能被当作新版本有效凭据；只要求重新质检，不改作者正文和既有历史。
6. 写清规则升级的作者可见影响并重建资产清单，之后重新冻结候选。

不授权时，此组保持待办；不能单独将“容易做”的部分先混入主线，也不能把 1.0.1 应用发布误写成规则 4.0.1 已生效。

- DK-14 延期的 #31/#37：函数清理与“末端失败改标注”分别立项；前者是重构，后者是作者可见的失败语义变更。
- foundation apply 对 `happened` 的整段替换：明确作者编辑与模型输出的优先关系，准备版本冲突和局部更新方案。
- 超过 400KB 的正文服务端写入校验：明确阈值含义和提示后补纵深保护，不能只依赖客户端按钮。
- 代码签名渠道：维护者决定采购与身份流程；若暂不采购，发行说明继续如实标注未签名。

### 12.6 明确不做，避免重新引入

- 不用“meta 只记哈希”替代可能是唯一历史副本的快照。
- 不按目录 mtime 返回可能陈旧的候选列表。
- 不自动按超时清锁，不自动删除作者 revisions。
- 不建立没有性能证据的常驻 Python 进程。
- 不为低频版本号同步新建当前并不存在的 bump-version 脚本；先用现有版本守卫核对。
- 不额外增加将被 T126 淘汰的 Node 22 CI 矩阵。
- 不把段落修订自动入草稿、第二供应商评审、空闲调度等新功能算作 1.0.1 漏项。
- UI-02 已有调用方 catch，不为不存在的吞错重复加包装。

## 13. S5/S6：候选冻结、发布与回退

### 13.1 冻结候选

1. 完成已批准的 T126、必要的遗留修复，以及如选择纳入的 T134。
2. 写明候选完整 SHA、Electron/Node/Python/规则版本、安装器和 ZIP 的哈希；代码改动后旧证据不自动继承。
3. 原生 Windows 最终完整运行 `verify:release` 或等价流水线，取得正确 SHA 的全部检查与包体证据。
4. 完成真机和批准的真实模型报告；未执行的门槛不能写通过。
5. 修正 STATUS、ACCEPTANCE、README、CHANGELOG 的计数与支持范围；记录已知问题与维护者的延期/豁免决定。

### 13.2 版本号和资源一致性

当前没有 `scripts/bump-version.mjs`，不要照旧方案运行不存在的命令。发布版本调整时核对：

- 根 `package.json`。
- `apps/desktop/package.json`。
- `packages/core/src/version.ts`。
- `package-lock.json` 中对应根与 workspace 的版本记录，通过合适的 npm 操作同步。
- CHANGELOG 第一条 `##` 标题的首个版本词。
- 包体内显示版本、安装器名、ZIP、更新元数据和源码归档。

正式发布目标如为 1.0.1，上述值与批准的标签 `v1.0.1` 一致。规则版本根据 T134 是否纳入，独立保持 4.0.0 或升级为 4.0.1。

版本号调整也会形成新 SHA；应在最终版本提交上重跑要求的检查及打包，不把 preview.1 包的报告当作 1.0.1 成品报告。

### 13.3 发布批准与执行

只有在维护者看到以下具体材料并批准后，才执行会触发发布的标签/工作流：

- 最终 SHA 与全部必需 job 的结果。
- NSIS、ZIP、SHA256SUMS、更新文件及签名状态。
- Windows W01–W20 记录。
- 真实模型报告，或明确批准的门槛变更。
- T134 是否纳入、规则版本、作者可见变化和已知限制。
- 回退办法及负责人。

当前 `release.yml` 会自动从校验进入上传发布，且要求标签指向构建 SHA。因此最后审批应在创建标签或触发该流程之前完成，不能把正式发布工作流当作“只生成草稿”的安全预演。

### 13.4 发布后冒烟

维护者在受控 Windows 环境核对下载链接、校验值、首次启动、既有作品打开、更新提示与实际升级。只执行已批准的模型请求；保留客户端/安装器版本和结果。

遇到阻断缺陷时：

1. 暂停推广/更新入口，明确告知受影响范围。
2. 保留坏版本产物和日志供定位，保护作者最新数据。
3. 按预演的回退流程恢复软件或从独立数据备份恢复；不覆盖作者在升级后新增的内容。
4. 修复采用新提交和适当的新版本，不移动旧公开标签或替换已下载的同版本包。
