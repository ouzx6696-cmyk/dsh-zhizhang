## 5. 打包与包体核对

普通推送的 CI 不走打包路径；`scope` 只在手动触发或标签上下文把 `package` 设为真，所以普通推送通过不代表 NSIS、ZIP、随包 Python 或更新文件已验。

候选提交推送后，由维护者或获授权的执行者手动运行 `ci.yml` 的打包路径，收集 `writer-windows-packages`，并用运行记录的 `head_sha` 确认构建的是预期提交：

```bash
gh run list --repo ouzx6696-cmyk/dsh-zhizhang --commit <候选完整SHA>
gh workflow run ci.yml --repo ouzx6696-cmyk/dsh-zhizhang --ref master
```

**不要用临时 `v*` 标签测试打包**，`release.yml` 会响应并直接发布；正式批准前也不手动触发 `release.yml`。

至少保存 NSIS、ZIP、blockmap、`latest.yml`、`RELEASE-CONDITIONS.json`、`SHA256SUMS` 及对应 SHA 和运行链接，并核对：

- ZIP 含 `WriterAgent.exe`、`resources/app.asar`、`resources/python/python.exe`、`resources/writer/scripts/writer-backup.mjs`。
- `latest.yml` 的版本、安装器路径、大小与摘要对应实际安装包。
- 随包 Python 能运行并输出中文，能导入头条与长篇脚本。
- 没有证书时如实记录未签名，不用 `signExecutable: true` 冒充已签名。
- 标签、源码版本、产物与构建 SHA 一致；不覆盖已发布的同版本包。

### 8.3 失败处理

- 丢稿、覆盖作者新稿、锁绕过、无法恢复、密钥泄漏、无法启动/安装：阻塞发布。
- 关键流程无法完成、错误费用统计、确认取消后半退出：阻塞发布。
- 纯样式问题由影响程度分级；关键操作不可达仍阻塞。
- 每次修复后重跑失败用例及受影响流程；运行时或安装配置改变时重跑整套安装/升级/卸载，而不是沿用旧截图。
- 退回旧程序前先对升级后的数据另做副本，保留新增内容；不能把恢复旧软件等同于允许覆盖新数据。

每个新增 bug 回归先证明修复前失败，再证明修复后通过。沿用现有 Node、Python、esbuild 组件运行时及 Playwright，不新建一套测试框架。

### 9.2 关键故障注入清单

| 编号 | 故障/输入 | 断言 |
| --- | --- | --- |
| R01 | 原子写/连续性 handoff 发布失败 | 不提前出现完成标记；可重试；原错误与清理失败同时可见 |
| R02 | 活锁、死锁、异机锁、损坏锁、owner 在确认时变化 | 只按既有明确条件处理；不按超时删锁；确认不能误作用于新 owner |
| R03 | journal 损坏/重复 step/负用量/请求损坏 | 读边界明确拒绝，保留原文件，不当成空任务 |
| R04 | 预算、余额、上下文、鉴权、普通 429/5xx、确定性 4xx | 分类、重试次数、暂停原因及保留进度正确 |
| R05 | 首次无输出 6 分钟、增量停滞 150 秒、持续 thinking、心跳无内容 | 停滞仅按实际进展重置；持续思考不误杀；停滞重试上限正确 |
| R06 | 并发任务池中一条暂停，其他请求尚未完成 | 不再派发；等待已启动请求结算；首次停止原因不被后续错误覆盖 |
| R07 | 暂停/重试/取消发生在已经返回部分用量后 | 所有计费用量保留，零用量不污染已知费用，未知费用保持未知 |
| R08 | 旧草稿键、旧修订恢复、localStorage 配额满 | 正确迁移/冲突拒绝；当前草稿不被清；失败不丢唯一副本 |
| R09 | 候选或 JSONL 读取期间替换文件、随后外部改写/删除 | 内容与文件身份匹配，污染隔离，变化后立即失效；持续变化有明确错误 |
| R10 | 来源私网、重定向回私网、凭据 URL、超 2MB、GBK、非法编码 | 安全边界不退化；编码/实体正确；非法标签明确失败 |
| R11 | 坏历史 meta、非法驱动、34 码点标题 | 坏历史可见跳过；非法驱动在起稿前重试；生僻字口径统一 |
| R12 | QA 精修改变正文、采用真实 QA 失败、恢复失败 | 事实链对应终稿；恢复原卡片字节和标题；恢复错误不掩盖首错 |
| R13 | 高频进度、晚到 status、任务最终状态与 dispose | 同任务旧快照不覆盖新快照；最终记录立即送达；无遗留 timer |
| R14 | 新任务覆盖确认取消、自动记账与暂停任务并存 | 原 current 指针和进度保留；记账排队且顺序正确、不重复 |
| R15 | 诊断字段和正文内混入凭据 | apiKey/token/Authorization/cookie、URL 凭据等均脱敏；maxTokens 等普通字段保留 |

涉及长等待和竞态的自动化优先使用已有假时钟、受控流或同步信号；不要把测试变成真实等待数分钟，也不要用固定 sleep 碰运气。

## 10. 真实模型测试与预算控制

### 10.1 先批准预算，后发生请求

维护者此前账户余额有限；未批准前不连接真实付费模型、不充值、不把连接测试当作免费操作。所有限流、余额、鉴权和恶意输入故障先用假模型模拟。

预算单必须包含：服务商、模型精确 ID、推理档位、经济档、两条任务内容、单任务及总费用上限、价格来源、允许的重试次数，以及超出估算时由谁决定停止。

注意：经济档“一章/一篇”也包含方法卡、规划、起稿、审读、事实链及可能的重试，**不等于只调用一次模型**。先盘点调用路径，保守估算输入、输出、缓存和重试成本，再确定额度。

客户端 token 预算不能当作严格的金额闸门。优先使用服务商能够实际执行的项目/密钥消费限额；没有该能力时，采用单任务串行执行、阶段边界人工核对、保守预留和明确停止条件，并披露无法保证精确金额硬上限。

### 10.2 两条必测业务路径

**RM01：经济档番茄一章。**

- 使用受控设定、已有章纲与适量正文，避免第一次测试就创建整本书。
- 执行起稿、择优/审读、修订、交付、作者采用、定稿与记账。
- 核对方法卡不含其他作品数据，阶段与终稿对应，硬伤有定位，暂停后进度仍在。
- 作者可评价文本可用性，但不以模型互评结果代替作者决定，也不宣称一次样本证明质量提升。

**RM02：经济档头条一篇。**

- 优先用已核对的作者素材，减少网络来源变化干扰；先跑卡片、标题、起稿，再跑事实链及现有 QA。
- 核对来源数字、引语、故事演绎标签和终稿事实链；实际采用失败须保留原卡片与标题。
- 记账后复检，核对没有不合理的自身比较；未实施 T134 时明确记录剩余规则边界。

已有真实任务中自然出现的长思考或可恢复暂停可以形成证据，但不为制造这些场景额外烧费。授权包含扩展推理档时再专项测试；否则仍使用看门狗模拟回归证明机制。

### 10.3 记录与停止条件

每条报告至少记录：

| 字段 | 要求 |
| --- | --- |
| 身份 | 源码 SHA、客户端/规则版本、服务商、模型、档位 |
| 任务 | 输入摘要、受控素材编号、是否冷方法卡/暖方法卡 |
| 时序 | 开始/结束时间、各阶段耗时、总墙钟时间 |
| 用量 | input、output、cacheRead、cacheWrite、各次 attempt；未知字段写未知 |
| 费用 | 客户端估算、服务商账单及币种；两者偏差和价格来源 |
| 结果 | 是否交付、是否通过 QA、作者是否采用、开放问题、暂停/失败原因 |
| 可恢复性 | 取消/重启后的状态、是否重复请求或重复交付 |

触达额度、报价无法确认、连续服务异常、出现数据保护问题或未经批准的新调用路径时停止。报告中保留失败和已计费用量，不删除失败记录制造“全程顺利”。

“未返回 cacheRead”不等于缓存未命中；“第二次较快”不等于命中率提升。需要收益对比时使用相同素材、模型、档位和缓存状态，单独批准额外成本后再测，不把本地算法基准换算成真实账单节省百分比。

结果写入 CHANGELOG 的“实测”说明，并保留脱敏原始记录。未执行或被停止的项目保持未完成；若维护者正式调整发布门槛，记录调整理由，不能默默省略。

## 11. T134：可选规则修订方案

T134 与普通稳定性修复分开提交。授权后只实施批准的条目，将 `rules.py` 的 VERSION 从 `4.0.0` 升到 `4.0.1`，更新变更说明和资产清单；应用版本号和规则版本号是两回事。

| 条目 | 实施内容 | 修复前应暴露的反例 | 修复后及反误杀验收 |
| --- | --- | --- | --- |
| TT-06 | 补明确占位符和 AI 自述短语 | `[待补]`、`【待补充数据】`、作为人工智能/AI 助手、本文由大模型撰写等原本可能漏过 | 明确占位/自述被拦；正常新闻中提到 ChatGPT、大模型、数字 X 等不被宽词误杀 |
| TT-07 | 标题数字用数字边界匹配 | 标题“5元”，正文只有“25元”却被当作接住 | 5 与 25、3.5 与 13.5、整数/小数边界正确；2.5万与25000换算不在本项 |
| TT-16 | 长图文缺小标题时明确失败 | 卡片有延伸要求但正文没有 `##`，主稿/延伸无法分查 | 明确报缺小标题；已有合法短图文和微头条不被套用长文规则 |
| TT-17 | 台账卡片比较优先按文章 ID 排除自己 | 同一文章改主标题后，复检和自己发生冲突 | 同 ID 排除自己；不同 ID 的真实撞题仍保留；旧行无 ID 时按批准方式兼容 |
| TT-18 | 有效 QA 绑定完整规则版本 | 旧 `4.0.0` 过线记录在 `4.0.1` 下仍可交稿 | 完整版本不等则要求重检；仅比较主版本不合格；同版本正常使用 |
| TT-25 | 将裸“AI生成”改为明确自指短语 | 正常报道“平台须对AI生成内容添加标识”触发身份泄漏 | 正常新闻不再被误杀；“本文由AI生成”等仍被拦；保留短语的范围严格按授权决定 |

实施顺序：

1. 用当前规则固化现有正例、反例及错误结果，取得基线。
2. 只修改已批准的词表/规则点，不改变 34/84/两轮等阈值，不借此重写方法原文。
3. 新增精确正反例，覆盖普通报道、引用他人声明、短数字、长文无小标题、自身台账、旧 QA 版本等。
4. 跑全部 Python 与 Node 业务用例、桌面两种模式和作者采用路径。已有过线夹具如改变结果，必须逐条解释，不调整夹具来掩盖误杀。
5. 核对旧 QA 可见但不能被当作新版本有效凭据；只要求重新质检，不改作者正文和既有历史。
6. 写清规则升级的作者可见影响并重建资产清单，之后重新冻结候选。

不授权时，此组保持待办；不能单独将“容易做”的部分先混入主线，也不能把 1.0.1 应用发布误写成规则 4.0.1 已生效。

### 12.5 还需明确业务语义的少量条目

- CORE-17：按钮意图与文本“询问”判断的优先级，须先明确产品语义，再用冲突输入测试。
- DK-14 延期的 #31/#37：函数清理与“末端失败改标注”分别立项；前者是重构，后者是作者可见的失败语义变更。
- foundation apply 对 `happened` 的整段替换：明确作者编辑与模型输出的优先关系，准备版本冲突和局部更新方案。
- 超过 400KB 的正文服务端写入校验：明确阈值含义和提示后补纵深保护，不能只依赖客户端按钮。
- 代码签名渠道：维护者决定采购与身份流程；若暂不采购，发行说明继续如实标注未签名。

### 12.6 明确不做，避免重新引入

- 不用“meta 只记哈希”替代可能是唯一历史副本的快照。
- 不按目录 mtime 返回可能陈旧的候选列表。
- 不自动按超时清锁，不自动删除作者 revisions。
- 不建立没有性能证据的常驻 Python 进程。
- 不为低频版本号同步新建当前并不存在的 bump-version 脚本；先用现有版本守卫核对。
- 不把段落修订自动入草稿、第二供应商评审、空闲调度等新功能算作 1.0.1 漏项。
- UI-02 已有调用方 catch，不为不存在的吞错重复加包装。

## 13. 候选冻结、发布与回退

### 13.1 冻结候选

1. 完成必要的遗留修复，以及如选择纳入的 T134。
2. 写明候选完整 SHA、Electron/Node/Python/规则版本、安装器和 ZIP 的哈希；代码改动后旧证据不自动继承。
3. 原生 Windows 最终完整运行 `verify:release` 或等价流水线，取得正确 SHA 的全部检查与包体证据。
4. 完成真机和批准的真实模型报告；未执行的门槛不能写通过。
5. 修正 STATUS、ACCEPTANCE、README、CHANGELOG 的计数与支持范围；记录已知问题与维护者的延期/豁免决定。

### 13.2 版本号和资源一致性

当前没有 `scripts/bump-version.mjs`，不要照旧方案运行不存在的命令。发布版本调整时核对：

- 根 `package.json`。
- `apps/desktop/package.json`。
- `packages/core/src/version.ts`。
- `package-lock.json` 中对应根与 workspace 的版本记录，通过合适的 npm 操作同步。
- CHANGELOG 第一条 `##` 标题的首个版本词。
- 包体内显示版本、安装器名、ZIP、更新元数据和源码归档。

正式发布目标如为 1.0.1，上述值与批准的标签 `v1.0.1` 一致。规则版本根据 T134 是否纳入，独立保持 4.0.0 或升级为 4.0.1。

版本号调整也会形成新 SHA；应在最终版本提交上重跑要求的检查及打包，不把 preview.1 包的报告当作 1.0.1 成品报告。

### 13.3 发布批准与执行

只有在维护者看到以下具体材料并批准后，才执行会触发发布的标签/工作流：

- 最终 SHA 与全部必需 job 的结果。
- NSIS、ZIP、SHA256SUMS、更新文件及签名状态。
- Windows W01–W20 记录。
- 真实模型报告，或明确批准的门槛变更。
- T134 是否纳入、规则版本、作者可见变化和已知限制。
- 回退办法及负责人。

当前 `release.yml` 会自动从校验进入上传发布，且要求标签指向构建 SHA。因此最后审批应在创建标签或触发该流程之前完成，不能把正式发布工作流当作“只生成草稿”的安全预演。

### 13.4 发布后冒烟

维护者在受控 Windows 环境核对下载链接、校验值、首次启动、既有作品打开、更新提示与实际升级。只执行已批准的模型请求；保留客户端/安装器版本和结果。

遇到阻断缺陷时：

1. 暂停推广/更新入口，明确告知受影响范围。
2. 保留坏版本产物和日志供定位，保护作者最新数据。
3. 按预演的回退流程恢复软件或从独立数据备份恢复；不覆盖作者在升级后新增的内容。
4. 修复采用新提交和适当的新版本，不移动旧公开标签或替换已下载的同版本包。

## 14. 排期、职责与投入建议

以下是资源齐备后的工程估计，不是承诺日期；授权等待、CI 排队和真机问题单独计时。
