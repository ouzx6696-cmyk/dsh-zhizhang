## 1. 总体评价

**一句话结论：** 骨架是干净的。IPC 契约有类型，聊天状态单独拆成了 store，流式输出用 rAF 合帧，消息组件做了 memo，设置和工作流按需加载，也有 CSP 和原生 `<dialog>`。但在**流式热路径**上有几处结构性浪费，把这些优化抵消了大半：主进程每个 token 都发送完整的消息快照；渲染层每个 token 都换一个新的 `task` 对象；全局 store 整体订阅。编辑器和工作流面板的体验比 DeepWrite 这类成熟产品低一个档次：没有自动保存和草稿恢复，阶段产出直接显示 JSON 原文，同时存在三种确认框，样式令牌（tokens）一半没有接上桥。

| 维度 | 织章 | DeepWrite（参考） | 理由（一句话） |
|---|---|---|---|
| 状态管理与重渲染 | 3 | 4 | 好的一面：聊天 store 已拆开，流式在 `ChatStream` 里隔离，`MessageView` 做了 memo。问题：`useDesktop()` 订阅整个 store，加上 `app` 每次渲染都是新对象往下传，查询词、焦点、上下文的任何变化都会让整棵树重渲染。 |
| IPC 往返与事件推送 | 2 | 4 | 每个 `message_update` 都带 `message` 和 `assistantMessageEvent.partial` 两份完整快照，长章节的传输量是 O(n²)；渲染层还有 3 个独立的 `subscribe`，每条事件要跨 contextBridge 复制 3 次。DeepWrite 有专门的事件映射层，只发增量。 |
| 流式输出与工作流面板体验 | 2 | 4 | 聊天侧有任务卡、计时和停止，基本够用。工作流面板是模态框，阶段产出直接 `JSON.stringify`，状态只有“完成/失败/进行中”三种，没有总进度和总用量，章节号要手填。DeepWrite 有处理时间线、运行计时、排队消息、改稿提案对比（diff）。 |
| 编辑器体验 | 2 | 4 | 改稿用的是“进入编辑模式”的 `<textarea>`：不自动保存，崩溃会丢稿，不能查找替换，用的是原生 `window.confirm`。DeepWrite 有自动保存协调、草稿恢复、查找替换面板、滚动位置记忆、保存状态提示。 |
| 组件结构与重复代码 | 3 | 4 | 按 feature 分了目录，主进程 IPC 统一走 `handle`。但控制器是个“大对象”，层层传下去；文案键没有语义（`agentPanelText1..53`）；用量格式化有 5 处各写各的；确认框有 3 套。 |
| 样式体系一致性 | 3 | 4* | 组件里没有一个硬编码 hex，一个前缀只出现在一个文件。但 `--wb-*` 只桥接了 2 个令牌，深色主题下“错误”和“通过”颜色几乎一样；间距令牌几乎没用（316 处写死 px，只有 2 处用了 var）；z-index 从 1 到 1100 没有分级。 |
| 可访问性 | 3 | 3* | 原生 dialog 自带焦点陷阱，有 `:focus-visible`、`prefers-reduced-motion`、步骤 `aria-current`。但流式输出和任务进度没有 live region，tablist 不完整，菜单和命令面板不能用键盘上下选。 |
| 首屏 / 启动速度 | 3 | 4 | 设置、引导、工作流、方法编辑器都是懒加载，渲染包有压缩，去掉了 woff。但窗口没有 `show:false` 和 `backgroundColor`，有白屏闪烁；启动时 IPC 串行，还重复调了一次 `state`。DeepWrite 有专门的主窗口启动闸门测试。 |
| **综合** | **2.6** | **≈3.9** | |

\* DeepWrite 的样式和无障碍没有逐文件核对，分数根据目录结构和抽看的实现估计（例如消息列表用了 `content-visibility: auto`，有 `ConversationViewportAnchor`、`EditorFindReplacePanel`、`useEditorAutoSaveCoordinator`、`useDraftRecoveryPersistence`、`ConversationRunClock`、`ComposerQueuedMessages`、`AgentEditProposalDiff`，`pi-runtime-adapter/src/event-mapping.ts` 把 PI 事件映射成只含增量的运行时事件）。

**值得保留的好做法：** `createStore` 浅比较后跳过无效更新；`useChatSelector` 细粒度订阅；`ChatStream` 用 rAF 合帧，并按 scope 和会话守卫；结果卡的 `handleJump` 用 ref 保持稳定；`Manuscript` 用 memo 并按字素切分标注；`ChapterList` 用 memo 并支持键盘遍历；IPC 契约加 `IPC_PARSERS` 做边界校验；一个 CSS 前缀只在一个文件出现（脚本核过，没有重复）。

## 2. 问题清单（按 收益 ÷ 风险 排序）

> 规模：S = 半天以内、单文件或少量文件；M = 1–2 天、跨模块；L = 需要设计或较大重构。
> “作者可见”= 按 AGENTS.md，需要任务单把它列为 bug 修复或体验改进才能动。

### P1　主进程每个 token 都推送完整的部分消息快照（IPC 传输量 O(n²)）
- **位置**：`apps/desktop/src/session/task-tracker.ts:285-315`（`forward`）、`apps/desktop/src/main/runtime.ts:47-50`（`emit`）
- **问题**：PI 的 `message_update` 事件同时带着 `message`（累积到当前的部分消息）和 `assistantMessageEvent.partial`（又一份完整快照），见 `node_modules/@earendil-works/pi-agent-core/dist/types.d.ts:467` 和 `pi-ai/dist/types.d.ts:577`。现在整个 `event` 原样 `webContents.send`，每次还附带 `task`、`focus`、`phase`。一章 6–8 千字大约 3–4 千个增量，每个增量都要结构化克隆两份“到目前为止的全文”，累计上百 MB。`thinking_delta`、`toolcall_delta`（工具参数里经常就是整章正文），以及编辑子会话（`editor: true`）的增量也照发，而渲染层根本不用（`useDesktopEvents.ts:124` 拿到 editor 事件直接 return）。
- **改法**：`forward` 里对 `message_update` 单独处理：只给主会话的 `text_delta` 发一个瘦事件 `{ conversationId, target, event: { type, assistantMessageEvent: { type, delta } } }`，其余增量不发。`renderer-contracts.ts:76-85` 里 `DesktopEvent.event` 的类型本来就是瘦形状，不用改契约。可选再加一步：主进程按约 16–33ms 合并 delta。
- **收益**：长输出时主进程 CPU、IPC 和 GC 压力大致降一到两个数量级，流式后半程掉帧会明显减少。顺带解决 P2。
- **规模**：S（见 §3 QW1）

### P2　渲染层每个 token 都写入新的 `task` 对象，`AgentPanel` 整体逐 token 重渲染
- **位置**：`apps/desktop/src/renderer/app/useDesktopEvents.ts:123`
- **问题**：`chatStore.set({ task: { ...value.task } })` 在每条事件上执行，每次都是新引用，`createStore` 的 `Object.is` 拦不住。`AgentPanel`（订阅了 `task`）连同 `ContextPanel`、`TaskProgress`、快捷按钮、输入区都会**在 rAF 合帧之外**逐 token 重渲染，`stream` 的 rAF 合帧白做了。主进程里 `task` 只在少数事件里变（`task-tracker.ts:177-182, 260`）。
- **改法**：首选 P1，增量事件不再带 `task`，问题自然消失。如果暂时不动主进程，就加一个浅比较守卫（字段相同就不 set）。
- **收益**：流式期间 React 提交次数从“每 token 一次”降到“每帧一次”。
- **规模**：S（随 QW1 一起）

### P3　渲染层 3 个独立的 IPC 订阅，每条事件跨 contextBridge 复制 3 次
- **位置**：`apps/desktop/src/preload.ts:71-77`；订阅方 `renderer/app/useDesktopEvents.ts:81`、`renderer/features/agent/ContextPanel.tsx:50`、`renderer/features/workflow/WorkflowPanel.tsx:156`
- **问题**：开了 contextIsolation 时，每个回调调用都会把事件对象复制进主世界。3 个订阅就是 3 次复制和 3 次反序列化，再叠加 P1 的大对象。
- **改法**：在 `renderer/state/desktop.ts` 做一个渲染层的事件总线：只挂一个 `writerDesktop.subscribe`，在内部用 `Set` 分发，三处改用 `onDesktopEvent`。
- **收益**：事件处理成本降到约 1/3，订阅生命周期也统一到一处。
- **规模**：S（见 §3 QW2）

### P4　全局 store 整体订阅加上“控制器大对象”下传，任何全局字段变化都会让整棵树重渲染
- **位置**：`renderer/state/store.ts:63`（`useDesktop` 返回整个 state）；`renderer/app/useDesktopController.ts:21, 288-323`（每次渲染返回新对象）；`renderer/app/App.tsx:55-117`（`app={app}`，以及 `setTab`、`onReview`、`onNewChapter`、`setDrawer`、`onTarget` 这些内联 lambda）
- **问题**：`running`、`focus`、`context`、`error`、`picker`、`query` 任何一个变化，`App` 都会重渲染，`TopBar`、`AgentPanel`、`CommandPalette`、`Workspace → Novel → Reader/Inspector/Diagnostics` 全部跟着重渲染。`ChapterList` 虽然有 memo，但 `onSelectChapter` 每次都是新 lambda（`Workspace.tsx:190`），memo 实际失效。
- **改法**：
  1. 照 `useChatSelector` 的样子给 desktopStore 加 `useDesktopSelector(selector)`，各组件只取自己要的字段。
  2. 把控制器拆成稳定的 `actions`（方法都经 ref 解引用，用 `useMemo(() => ({...}), [])` 只建一次）和数据两部分；`TopBar`、`AgentPanel`、`CommandPalette` 接收 `actions`，数据自己选。
  3. `App.tsx` 的回调改成 `useCallback`，`Workspace` 和 `Novel` 包 `React.memo`；`Workspace.tsx:185-194` 的回调用 `useCallback`。
- **收益**：切换面板、错误提示、后台任务状态变化时，不再重渲染阅读器和章节列表。长书（几百章）切换明显更跟手。
- **规模**：M

### P5　命令面板的查询词放在全局 store，每敲一个键整棵树重渲染；不能用键盘选择
- **位置**：`renderer/features/palette/CommandPalette.tsx:21-36`；`renderer/state/store.ts:35, 55`；写入点 `useDesktopShortcuts.ts:28`、`AgentPanel.tsx:223, 243`、`TopBar.tsx:135`、`commands.ts:154`
- **问题**：① 敲一个键 → `desktopStore.set({query})` → 整棵树重渲染（见 P4）；② 没有 ↑/↓ 选择和 Enter 执行，没有当前项高亮，也没有 `role="listbox"` 和 `aria-activedescendant`；③ 匹配只是 `includes`，没有模糊或拼音匹配，也不按当前模式（番茄 / 头条）过滤命令，不显示快捷键。
- **改法**：`query` 改成组件内 `useState`（面板本来就是条件挂载，每次打开自动清空），从 `DesktopState` 删掉 `query`。加 `active` 下标，处理 ↑/↓、Enter、Home/End，列表加 listbox 语义。模糊和拼音匹配放到后续。
- **收益**：输入不再卡顿（尤其打开长书时），命令面板达到 VS Code / Obsidian 的基本可用水平。
- **规模**：S（见 §3 QW3）

### P6　流式 Markdown 每帧都从头解析全文
- **位置**：`renderer/features/agent/AgentMessages.tsx:29-38`（`<Markdown text={stream} />`）；`packages/ui/src/markdown.jsx:43-53`
- **问题**：`react-markdown`、`remark-gfm`、`rehype-sanitize` 每帧都对整段 `stream` 做完整的 parse 和 reconcile，输出越长每帧越贵（7–8 千字时估计每帧 5–15ms），叠加 P1、P2 后后半程会掉帧。
- **改法**：按段落（空行）把流切成多个块，代码围栏里不切。已经闭合的块各自交给 memo 过的 `<Markdown>`，只有最后一块随 token 重新解析。`message_end` 之后会被正式消息替换，所以跨块的细微渲染差异（例如松散列表编号）只是暂时的。
- **收益**：每帧解析量从 O(全文) 降到 O(当前段)。
- **规模**：S（见 §3 QW4）

### P7　Esc 键冲突：关菜单时连带关掉侧栏或弹出“停止任务？”；编辑态下 Esc 关不掉对话框（bug）
- **位置**：`renderer/features/topbar/TopBar.tsx:37-41`（监听 document，不 preventDefault）、`renderer/app/useDesktopShortcuts.ts:22-58`（监听 window，只看 `defaultPrevented`）；`packages/workbench/src/client/shared/SourceEditor.jsx:57`
- **问题**：
  1. 打开项目菜单或导出菜单后按 Esc：TopBar 关了菜单，事件继续冒泡到 window，全局处理器发现没被 preventDefault，于是任务运行时弹“停止当前任务？”，空闲时把右侧抽屉也关了。
  2. `SourceEditor` 在捕获阶段监听 Esc 和 Ctrl+S，用 `[aria-modal="true"]` 判断是否有模态框，但全仓库没有任何元素设置 `aria-modal`（原生 `showModal()` 不会加这个属性）。所以编辑正文时打开命令面板或确认框，按 Esc 会被编辑器截走（preventDefault 加 stopImmediatePropagation），对话框关不掉，反而进入“放弃修改”流程。
- **改法**：TopBar 的 escape 处理器在真正关闭菜单时调用 `event.preventDefault()`。SourceEditor 的判断改成 `document.querySelector("dialog[open]")`，和全局快捷键保持一致。
- **收益**：修掉两个确定能复现的交互 bug。
- **规模**：S（见 §3 QW5）·作者可见（bug 修复）

### P8　`--wb-*` 令牌只桥接了一部分，深色主题下工作台“错误 / 通过 / 警告”用的是系统色
- **位置**：`apps/desktop/src/styles/base.css:118-124` 只映射了 `--wb-fg` 和 `--wb-accent`（另外映射的 `--wb-muted`、`--wb-surface`、`--wb-border` 没有任何地方使用）；`packages/workbench/src/client/styles/base.css:12-37` 的默认值基于 `canvastext/linktext/mark`
- **问题**：`--wb-bad = mix(canvastext 55%, linktext)`、`--wb-ok = mix(linktext 30%, canvastext)`，在深色主题下都是偏蓝的浅灰，“错误”和“通过”几乎分不出来，和桌面端琥珀色调的 `--ui-danger #e8857a`、`--ui-success #8fc29f` 也不一致。`--wb-fg-2/3`、`--wb-line*`、`--wb-hover`、`--wb-accent-soft` 等也没跟随主题（共 261 处 `var(--wb-…)`）。另外 `--wb-font-step` 没有默认定义，只靠 fallback 撑着。
- **改法**：在 `.writer-desktop` 下把剩余的 `--wb-*` 全部映射到 `--ui-*`，删掉 3 个没用的映射。
- **收益**：一处 CSS 修好工作台在两套主题下的语义色，视觉统一度明显提升。
- **规模**：S（见 §3 QW6）·作者可见（视觉修正）

### P9　启动：白屏闪烁 + IPC 串行 + 重复调用 `state`
- **位置**：`apps/desktop/src/main/window.ts:9-20`（没有 `show:false`、`backgroundColor`、`ready-to-show`）；`apps/desktop/index.html`；`renderer/app/useDesktopEvents.ts:44-51`；`renderer/app/useDesktopController.ts:130-132`
- **问题**：① 窗口创建后马上显示，默认白底，深色主题用户每次启动都会看到白屏一闪，主题要等 `syncState` 之后才设置；② 启动链路是 `state → select(...) → state(重复) → view → conversations → running → projects`，全部串行 await，其中 `running`、`projects`、`conversations` 互相不依赖。
- **改法**：窗口按已保存的主题设置 `backgroundColor`，加 `show:false` 和 `ready-to-show`；`loadFile`/`loadURL` 带上 `?theme=`，`App.tsx` 在挂载前先把 `data-theme` 设好。`running` 和 `projects` 用 `Promise.all` 并发；`conversations` 和 `loadView` 并发。
- **收益**：消除启动闪烁，首屏可交互时间少几次 IPC 往返。
- **规模**：S（见 §3 QW7）

### P10　工作流历史在每次阶段发布时都整表重新拉取
- **位置**：`renderer/features/workflow/HistoryPane.tsx:31-45`（依赖 `updated`）；`WorkflowPanel.tsx:313-318`
- **问题**：`value.updated` 每次 journal 保存都会变，于是每次都调用 `workflowHistory`，把所有历史记录（含各阶段 output、草稿正文）完整读一遍并跨 IPC 传过来。
- **改法**：依赖改成“记录 id + 状态”（`value?.id`、`value?.state`），只在开始、结束、暂停这些节点刷新。
- **收益**：工作流运行期间 IPC 和磁盘读取明显减少。
- **规模**：S（见 §3 QW8）

### P11　焦点和上下文回传引起的双重整树重渲染
- **位置**：`renderer/features/workspace/Workspace.tsx:52-78`（`onContext` 每次传新对象）；`packages/workbench/src/client/fanqie/useFanqie.js:176-215`（`targetSink` → `selectSnapshot` → `useDesktopController.ts:44-47 setPosition` 每次传新 `focus`）
- **问题**：章节状态一有变化（加载、元数据、诊断）就要调用两次 `desktopStore.set`，每次都是新对象，叠加 P4 就是两次整树重渲染。
- **改法**：`setPosition` 和 `onContext` 写入前先做浅比较（字段逐个 `Object.is`，`actions` 比较函数引用），没变化就不写。
- **收益**：章节切换和加载过程中少 1–3 次整树提交。
- **规模**：S–M

### P12　点结果卡“查看”或任何 jump 都会让整个写作区重挂载
- **位置**：`renderer/app/App.tsx:58`（`key` 里包含 `workspaceKey`）；`renderer/app/useDesktopController.ts:201`（每次 jump 都 `workspaceKey + 1`）
- **问题**：即使在同一部作品里跳到另一章或候选稿，也会卸载 `Novel` 和 `useFanqie`，丢掉阅读滚动位置、诊断状态、章节列表的筛选；重新读快照，骨架屏闪一下。
- **改法**：只在作品范围（`scopeId`）真正变化时才 bump。同一作品内的跳转通过 `useFanqie` 已有的 `dispatch({type:"selectChapter"|"selectCandidate"})` 完成，需要给 Workspace 暴露一个 `navigate(focus)` 入口（可以挂在 `context.actions` 上）。
- **收益**：“结果卡 → 原文”从“整页重载”变成即时切换，这是 Cursor 和 Notion AI 那类“点了就到”体验的关键。
- **规模**：M（要理顺 prefs 驱动的初始化，有回归风险）

### P13　工作流面板：模态框、JSON 原文、状态不全、没有总进度
