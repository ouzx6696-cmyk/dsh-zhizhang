# 0.9.3 开发指导

本文件把[需求计划](PLAN-0.9.3.md)落实为工作包。状态：实施中；已完成部分见实施记录，下面尚未完成的约束不能视作已有能力。结果填写到[验收报告](0.9.3-ACCEPTANCE-REPORT.md)，具体用例见[验收规范](0.9.3-ACCEPTANCE.md)。

## 1. 开发约束

1. 以已内置 PI 的自有客户端为主线。使用现有 checkout，保留用户改动；云任务已有隔离，不自动创建 worktree。先读取适用的 AGENTS.md。
2. 保持 `apps/desktop/src/pi.ts` 为 PI SDK 导入边界。先核对锁定的 1.4.0 实际接口，再处理生命周期、压缩、取消和历史；不能根据最新版在线示例臆造本版 API。
3. PI 的会话及 JSONL 是聊天事实来源，作品文件是创作事实来源；现有内存任务信息只作运行投影。不增加聊天数据库、持久任务中心或第二个 Agent 循环。
4. 正文、候选、章纲、审读、已发生与锁定按现有格式和规则工作；作品写入复用现有存储、锁、Journal、快照与指纹机制。
5. 上游方法原件和默认方法内容不在工程重构中顺带改写；不为假模型或测试通过调整质量阈值。若真实验收发现具体方法问题，另记证据和范围。
6. 实现与必要回归同包交付。沿用当前测试入口，优先在既有场景补充真正能失败的断言；不为每个工作包再造一套烟测或端到端目录。
7. 新版本功能按包实现，不把整个根目录移动或全部 imports 改别名作为前置任务。版本号在交付候选阶段统一核对，规划阶段保持 0.9.2。

## 2. W0：固定基线和执行契约

对应 R03／R09／R10；先于其他工作包。

检查入口：`package.json`、锁文件、`desktop/pi.ts`、`session.ts`、`context.ts`、`main.ts`、`test/desktop/runtime.test.mjs`、`ui.spec.mjs`、`scripts/acceptance.mjs`。

执行步骤：

- 记录代码 SHA、工作区状态、Node／Python／PI／Electron／操作系统版本，建立本轮独立证据目录。
- 运行已有业务与桌面核心检查，区分源代码缺陷、环境失败和未执行；与 0.9.2 审查基线比较。
- 从锁定 SDK 的实际类型、代码及既有测试确认：提示接收时机、串行工具执行、isIdle、主／子会话 abort、compaction／retry 事件、消息 entry ID 和分支、持久化消息及会话恢复方式。
- 固定内部数据的责任归属：会话范围 Target；页面 Focus；发送时任务对象及版本；角色；工具结果；作者决定。复用现有类型，缺少的字段按使用点补齐，不造通用协议框架。
- 在临时目录复现长篇确认缺口和台账竞态，保存调用、返回和磁盘结果。开始实施后用同一反例验证修复。
- 创建真实 E 集配置样例和固定性能样本。有凭据时核对已有安全绑定并运行真实旧版基线；缺少时记录条件，继续其他工作，不在聊天或报告中收集 Key。

交付：基线记录、SDK 行为核对清单、工作包实际缺口及投入估算。退出条件：确认本版要改的行为及其证据，不把已经实现的能力再列为新增。

## 3. W1：作者决策和头条台账

对应 R01／R02；依赖 W0；验收 A01～A07。

### 修改入口

- `packages/core/src/gates.ts`、`host-generic/src/index.ts`。
- `packages/fanqie/src/gates.ts`、`engine/bootstrap.ts`、`engine/tools/works.ts`、`engine/tools/candidates.ts` 与相关作者动作接口。
- `packages/toutiao/src/tools.ts`、`store.ts`、`workbench/data.ts`、`skill/scripts/writer_bridge.py`、`ledger.py`。
- `desktop/main.ts` 的确认与 IPC，`session.ts` 的工具封装。

### 操作指导

1. 追踪 PI 工具调用与作者 UI 调用两条路径，列出定稿、force 修订、采纳和采用的对象、版本及授权来源。可信内部存储接口不暴露为模型可自行授权的接口。
2. PI 执行入口在作者实际同意后才允许敏感执行；确认与本次调用、参数和所读版本绑定，使用一次即失效。缺失、取消、拒绝、版本变化不得靠默认值继续。`evaluate` 返回 ask 不等于作者批准。
3. 在工具边界补齐防漏接检查，并核对写入事务内的版本条件，避免仅在弹窗前检查。保留作者 UI 的 expectedRevision／rev／sha256 校验；不增加重复弹窗。
4. 对台账把“读取现有记录→查重→追加或改状态→写入”作为整体互斥操作；统一所有写入口，不只包住最后的 Python 调用。使用规范路径避免路径别名产生两把锁，避免嵌套串行锁死锁。
5. 新记录绑定稳定文章身份；必要的身份字段以兼容方式加入，明确旧记录缺字段时的策略。旧标题变化或旧台账歧义不能导致误合并；不要未经记录整体迁移或去重作者 CSV。
6. 原子写入使用同目录临时文件并正确清理；并发锁负责防丢更新，原子替换负责防半写。多开客户端继续受已有作品租约限制；不要重用长篇私有锁而引入跨包倒置依赖。
7. 敏感提交已经完成但通知失败时保留真实提交结果，单列通知错误，不要求作者盲目重做。

回归位置：`test/fanqie.test.mjs`、`test/flow.test.mjs`、`test/unit.test.mjs`、`test/desktop/runtime.test.mjs` 及存储测试中相关场景。共享行为变化时运行既有 DSH 检查，维持存量兼容，不开发新适配器。

交付：授权／版本责任清单、台账兼容说明、并发与中断证据、对应回归。

## 4. W2：PI 会话、取消和内部结果契约

对应 R03／R06；依赖 W1 确认接口；验收 A08～A12、A19。

修改入口：`desktop/pi.ts`、`session.ts`、`context.ts`、`main.ts`、`diagnostics.ts`；公共工具执行和错误边界按实际需要调整。

执行步骤：

- 沿现有 Sessions 管理会话初始化、current／history 指针及释放。对初始化中的重复 open、任务接收失败、后续模型失败分别处理；同一请求不得因 IPC 重试产生第二次任务。
- 用 PI 事件和 isIdle 投影运行状态；区分运行中、等待作者、取消中、结束、失败。它们是显示状态，不是自建持久调度器。
- 每次发送复制并固定目标、页面所指对象和已保存基线；消息排队时仍保留原始对象。开始执行时发现基线变化，应重读或报告冲突，不能悄悄对新版本执行旧命令。
- 将取消从主任务传到正在创建和正在运行的编辑／规划子会话、网络、Python 与确认等待。处理 child 注册前已取消的竞态；移除监听、释放子会话只在实际收尾后进行。
- 原子事务进入提交前检查取消；提交中断点遵循已有事务与恢复规则，不强行截断作品写入。UI 最终显示究竟保存了什么。
- 重启使用现有 PI 文件和作品状态恢复，未完成工具／回报标为待核对；继续由新指令触发，不自动重播已执行工具。
- 定义可供 PI 工具结果和桌面结果卡共同使用的内部成功／失败投影。至少保留业务码、中文说明、对象、版本及产物身份；不能把中文“错误”前缀当程序协议。
- 保留领域错误，例如 revision_conflict／resource_locked／recovery_required；作者取消与业务失败区分。生成过程可结束但没有有效产物时，不发“稿件完成”通知。

拆分原则：只抽出生命周期、工具执行或结果投影中能减少混杂职责的部分；命名与规模在实际修改中确定，不强制重建所有包的 index.ts。

交付：状态／事件对照、结果类型与错误映射、取消及重启证据。

## 5. W3：角色能力和产物交接

对应 R04；依赖 W2；验收 A13～A15。

修改入口：`desktop/session.ts`、`models.ts`、`pi.ts`、两种模式的工具工厂和角色规则、`review.ts`、候选工具。

执行步骤：

1. 从实际工具定义形成 writer／editor／planner 的能力表。记录工具是否读作品、写正文、写规划、暂存候选、采纳或更改终态；混合工具按参数约束。
2. 编辑能力必须包括必要的章纲、根基、前文、候选、诊断和回报；移除与审读无关的拆书入库和灵感写入。不要照搬第三方不存在的工具名，也不以固定工具数量代替可用性。
3. 规划保留开书、章纲与拆书实际流程，禁止正文写入和正文采纳等超出职责的动作。工具未注册与执行拒绝两层都验证；只在提示词写“不许”不算完成。
4. 写手保留委派工具；编辑／规划不再派生子任务。复用现有角色模型选择、独立内存上下文与 abort，不建立新 Agent 调度层。
5. 回传现有产物 ID、对象和版本。检查写手发出的任务、子角色实际操作对象及回报一致；旧回报、错误对象、无回报分别显示，不把任意最近一份旧回报当成本次完成证据。

交付：实际角色能力表、交接数据说明、正向和拒绝场景。工具 schema 大小可记录字节或实际 token，禁止把字节换算结果写成已测首字延迟。

## 6. W4：上下文和跨章连续性

对应 R05；依赖 W2／W3；验收 A16～A18。

修改入口：`desktop/context.ts`、`session.ts` 的 taskPrompt／handoffPreview，现有 chapter_brief、依赖与审读实现，方法方案读取入口。

执行步骤：

- 复用精简交接，明确已保存版本、写作／审读／规划意图及当前方案；正文和方法仍按任务由工具读取。
- 校验派编辑、排队任务、新建书归属、切换作品时传递的对象；不根据用户恰好浏览的页面推断后台工具目标。
- 压缩和新对话后核对必要的章纲、前章正文、锁定、已发生和候选依赖；使用 PI 已有压缩，不造全书记忆数据库。
- 修改前章时沿用已有影响记录和审读指纹失效规则；后章已有定稿不被自动重写。核对之后再由作者按原规则决定。
- 规划和只读检查不因关键词误判而强制写章简报或变更作品；在可确定的 UI 动作中优先传显式 intent，保留自由文本的合理处理。
- 方法切换和作者偏好生效时机清楚；未保存正文／方法草稿经过现有离开检查，不能成为模型误以为已保存的依据。

交付：各任务最小依据清单、上下文样例和跨章证据。真实 E 集的问题再回溯到具体上下文或方法位置，不整体增大每轮 prompt。

## 7. W5：作者反馈和长历史

对应 R06／R07；依赖 W2／W4；验收 A19～A22。

修改入口：`desktop/session.ts` 的 history／view、`client.jsx`、`Workspace.jsx`、`preload.ts` 与相关 IPC 类型。

执行步骤：

- 界面消费结构化结果和真实产物；更新步骤完成、通知、结果卡和跳转，覆盖业务返回失败但模型回合正常结束的情况。
- 使用 SDK 稳定 entry／message 身份，明确快照和流式事件如何对应；保留顺序和分支，不用 role＋timestamp 充当唯一 ID。
- 先定位实际开销，再做有界缓存／按需投影。缓存键覆盖会话文件、实际分支和读取范围；文件追加、替换、截断和新对话使相应缓存失效。不要以更改或清空历史提速。
- 初次 80 条、旧消息展开、实时消息缓冲合并和旧对话查看共同验证；作品 A／B 切换时丢弃迟到的旧请求响应。
- 使用固定样本测量冷／热加载、页内操作和内存，前后同环境同脚本。数据不足时保留限制，不宣称 O(1) 或具体提升比例。
- 保留 1440／1100／900 宽度、阅读对照和未保存保护；不同时做编辑器和整套视觉重设计。

交付：消息身份与失效策略、性能样本及原始测量、结果卡和布局截图。

## 8. W6：占用和恢复诊断

对应 R08；依赖 W1，使用 W2 的错误契约；验收 A23～A24。

修改入口：`core/workspace-lock.ts`、长篇 `storage/process-lock.ts`／`recovery-common.ts` 及各 Journal 的既有 inspect/resume、桌面设置／诊断入口和备份脚本。

执行步骤：

- 先做只读诊断，区分活进程占用、同机失效租约、待核对资源锁、待恢复 Journal 和状态未知；不把超时视作失效证明。
- 显示问题对应的作品与安全下一步；诊断区提供既有备份和受控恢复入口，普通写作流程不展示底层协议细节。
- 复用恢复函数的文件范围、before／after 哈希与原所有者检查。资源锁仍阻止调用恢复时，不能直接绕过锁；未能证明安全解锁的场景明确保留只读和人工核对。
- 恢复前创建并校验备份；恢复后检查正文、索引、候选状态和 Journal 一致；重复调用不重复应用结果。
- 异机、活进程、所有权未知、文件冲突和备份失败均不自动清理或重放；保留诊断证据，不吞错误。

交付：状态到作者提示的映射、安全恢复条件、拒绝与成功证据。实现的是有限的恢复向导，不是自动修复所有损坏文件。

## 9. W7：架构、类型和存量兼容

对应 R09；从 W0 开始随包实施；验收 A25～A27。

- `architecture-guard.mjs` 纳管 desktop 的主进程／preload／renderer，继续保留现有包分层和依赖环检查；确认 renderer 不能穿入 Node 存储，PI SDK 不散落到其他文件。
- 桌面自有 `.ts/.tsx/.js/.jsx` 入口和渲染文件纳入类型检查，可按文件使用 TSX 或有检查的 JSDoc；声明复用共享 JS 组件的边界。先补 React／IPC／业务对象的实际类型，不用关闭检查或全局 any 通过。
- 守卫要识别实际使用的 import／export／动态导入及相应扩展名；规则必须有违反边界的反例验证，不能只证明当前扫描返回零问题。
- 检查源码与打包后的加载方式；确需别名或依赖调整时，同时修改构建解析和锁文件，并解释必要性。
- 两种写作模式、方法方案、资料限制、加密配置降级、导出、快照和备份保持回归。旧数据夹具只用副本，记录打开前后变化；只读打开不应改写业务文件。
- 共享内核有改动时执行原有 DSH 集成和两条 headless；它们是存量回归，不产生本版新的适配功能。

交付：架构规则覆盖范围、类型检查覆盖文件、兼容记录、同提交构建和 CI 证据。

## 11. 每个工作包的提交内容

每包的说明至少包含：对应 R／A 编号、具体触发与前后行为、修改范围和数据兼容方式、实际执行的命令和结果、证据路径、未完成项与下一包依赖。同步填写验收报告，不能留到最后凭记忆宣称全通过。

业务源代码变化后运行相关既有检查；通过后按受影响范围扩大到完整入口，不为文档编辑反复运行整套应用测试。验收使用同一最终提交；后续代码变化使证据失效时，重跑受影响检查并记录新 SHA，不沿用旧包的通过结论。
