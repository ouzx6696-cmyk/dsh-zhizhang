日期：2026-11-01（香港时间）

> 后续状态：本报告保留固定基线的审查事实；对应修复与校验见 [审查修复记录](0.9.2-REVIEW-FIXES.md)。

## 审查结论

**架构方向可以保留，当前版本仍需修正对象与版本在边界处的传递，再进入正式发版验收。** 本轮确认 8 类问题：3 项 P1、5 项 P2；没有发现需要推倒写作内核或再增加一套宿主框架的依据。

项目的核心用途是让作者围绕本地作品连续创作：模型推进规划、写作和独立编辑，工具保存作品事实，作者对所读版本作出采纳、采用和定稿决定。审查以这条完整链路为尺度，不评价或改写写作方法论。

0.9.2 已把独立客户端所需的大部分入口接起来，业务复用、独立子上下文和原生 Windows 构建均有实际证据。剩下的问题主要集中在三个边界：页面正在展示的对象是否就是动作要处理的对象；导出和验收是否读取对应版本的真实数据；租约、配置及发布引用能否完整收尾。

## 范围与证据边界

本轮重点追踪桌面 React 状态、IPC、Pi 会话与角色、共享存储和作者动作、导出、作品租约、配置恢复、验收统计及 Release 工作流，并回看相关 DSH 共享路径。没有逐份重新评判方法资产，也没有把源码检查描述为真实模型创作验证。

没有修改业务代码，没有新增测试用例或重跑整套测试。定点核对只在临时目录使用构造作品和本地假模型；汇总反例的质检元数据和分数明确是构造资料，不能当作真实写作验收。既有 Windows CI 全绿作为基线证据，本轮发现的问题并未被现有场景充分覆盖。

P1 表示应在正式交付或使用真实验收结果作判断前解决；P2 表示正常功能、恢复或可用性缺陷。这里的等级不等同于漏洞等级，也不表示已经发生作者数据损失。

## R1 · 头条“采用”缺少已加载对象与版本约束

**影响：作者读过第一版，最终标记“已交稿”的可能是后来生成的第二版。** 这条路径没有绕过质检；缺失的是作者所确认版本与实际采用版本之间的对应关系。

触发方式一：页面已加载文章第 1 版，后台生成第 2 版并再次验收，作者随后确认采用。客户端只提交 root、id、confirm；服务端重新取得当前文章，校验当前质检后直接更新状态，没有接收或比对页面已加载的 rev / sha256。

定点复现结果：`loadedRevision=1`、`adoptedRevision=2`、`status=已交稿`。复现用构造的合格状态隔离版本问题，没有声称两份文字经过真实质检。

触发方式二：从已验收的 A 切到 B，B 详情尚在加载时，useToutiao 暂时保留 A 的 detail.article；新中栏按钮仍根据 A.adoptable 判断是否可点，而 actions.adopt 使用 selected B。该路径从源码可确定，未进行带人为延迟的 Electron 重演。

证据：[packages/workbench/src/client/shared/api.js:123](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/workbench/src/client/shared/api.js#L123)；[packages/toutiao/src/workbench/data.ts:80](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/toutiao/src/workbench/data.ts#L80)；[packages/workbench/src/client/toutiao/useToutiao.js:48](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/workbench/src/client/toutiao/useToutiao.js#L48)、[packages/workbench/src/client/toutiao/useToutiao.js:115](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/workbench/src/client/toutiao/useToutiao.js#L115)；[apps/desktop/src/Workspace.jsx:303](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/Workspace.jsx#L303)。

最小修正：采用动作捕获实际加载的 root、id、rev 和正文指纹；详情未就绪或与选中对象不匹配时禁用。服务端在同一串行更新中复核这些依据。可沿用长篇已实现的 expectedRevision 思路，不需要新增审批系统。这是既有头条动作契约的缺口，0.9.2 的新中栏入口也继承了它。

## R2 · 真实模型验收的编辑通过率没有核对正文版本与角色

**影响：回报已经过期，自动统计仍可能显示 100% 编辑通过率。** 如果据此比较默认与原版，会把没有审读当前稿的记录纳入结果。

summarize 读取每章最新回报，只检查 verdict 和 reread_full；没有将 body_sha256 与当前正文对照，也没有要求回报 by 为 editor。日常写作界面的 chapterReviewInfo 已具备过期判断，验收脚本没有复用。

定点反例使用真实存储函数：默认与原版各建 10 章，先记录通过回报，再修改每章正文。现有 chapterReviewInfo 确认 20 份回报全部过期；汇总仍给两套方案各记 `editorPassRate=1`、`automaticThresholdsMet=true`。

作者评分保留未填，所以脚本没有宣布最终验收通过。这个人工检查仍然有效；问题在于自动指标已经失真。此外，任务完成目前以 Agent 结束为依据，样本类别、逐任务产物与回报的映射主要靠目录数量，尚不能充分证明指定的验收集全部按要求完成。

证据：[scripts/acceptance.mjs:92](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/scripts/acceptance.mjs#L92)、[scripts/acceptance.mjs:141](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/scripts/acceptance.mjs#L141)、[scripts/acceptance.mjs:287](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/scripts/acceptance.mjs#L287)；[packages/fanqie/src/review.ts:102](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/fanqie/src/review.ts#L102)。

最小修正：按任务记录定位实际书、章和文章；用现有正文指纹与回报有效性逻辑统计，并要求独立编辑身份。缺稿、过期回报和缺少指定产物应单列，不能计入有效通过的分子；分母仍以约定验收集为准，缺项保留未完成，不能被“任务结束”替代。本项应在花费真实模型费用跑完整 E 集之前修正；不需要据此改写写作方法。

## R3 · Release 工作流没有保证已有标签指向本次构建提交

**影响：附件可能来自 0.9.2 开发提交，Release 自动生成的标签源码却来自其他提交。**

工作流核对 package.json 的版本、草稿状态和文件校验值，随后调用 `gh release edit --target "$GITHUB_SHA"`。它没有检查已有 Git 标签最终解析到的 commit。GitHub 官方接口对 target_commitish 的说明明确写着：**“Unused if the Git tag already exists.”** 更改 Release 的 target 字段不能代替核对或更新已存在的 Git 标签。

触发条件：先在默认分支上创建 v0.9.2 草稿及对应标签，再在开发分支运行本工作流。版本字符串检查可以通过，现有标签仍可能指向另一个提交。本轮没有创建实验 Release 或移动任何标签；这个结论来自可确定的接口语义。

证据：[.github/workflows/release.yml:30](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/.github/workflows/release.yml#L30)；[GitHub 官方 OpenAPI 中的更新 Release 定义](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)，路径 `/repos/{owner}/{repo}/releases/{release_id}` 的 PATCH、target_commitish 字段。

最小修正：上传和转正式发布之前，解析标签最终指向的提交，与被 CI 验证的构建 SHA 比较；不一致时停止并明确指出差异。不要把自动强制移动已有正式标签作为默认处理。这是旧工作流沿用到本版的缺口。

## R4 · 候选结果卡没有绑定刚生成的候选

**影响：点击“候选稿 → 对照查看”会打开现行正文；已有多份候选时也不能保证定位到这次生成的那份。**

session.ts 将候选工具结果标成 candidate，但 resultFocus 只补 chapter / article，没有保存实际生成的 candidate ID。前端 remember 又只根据 focus.candidate 决定是否打开候选视图；因此从正文发起写作时，点击结果卡会回到正文。即使带上某个候选 ID，当前阅读偏好也没有将该 ID 完整传给新挂载的候选选择状态。

真实 Pi＋本地假模型复现：工具确实返回“候选已暂存：cand-…”，writerResult.focus 只有 intent 和 chapter，没有 candidate。

证据：[apps/desktop/src/session.ts:280](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/session.ts#L280)；[packages/fanqie/src/engine/tools/candidates.ts:55](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/fanqie/src/engine/tools/candidates.ts#L55)；[apps/desktop/src/client.jsx:48](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/client.jsx#L48)、[apps/desktop/src/client.jsx:336](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/client.jsx#L336)。

最小修正：从候选暂存的实际结构化结果传递 candidate ID，并在跳转后显式选中这一份。保留人类可读回执，避免靠解析中文回执重建工具事实；沿用现有作品和候选选择状态即可。

## R5 · 导出没有形成独立、完整的发布正文

**影响：正常头条样稿导出后仍混有配图提示与重复标题；超长稿件还可能只输出预览部分。**

对仓库 story_long_good.md 的实际核对显示：导出文本保留 5 处 `【配图：…】`，标题出现 2 次。原因是清理规则识别“配图提示／配图建议”等词，却没有识别本项目模板实际使用的“配图”；外层又在已经含标题的稿件之前再加一次标题。

更深一层的问题是 exportContent 使用工作台 articleDetail 作为导出数据源。该查询会在 200,000 个字符处截断预览。构造长度边界核对中，末尾唯一标记丢失，导出正文包含“已截断”，发布检查的 issues 却没有专门指出截断。这个长度不是普通头条稿件的典型规模，但确认了预览层限制进入正式文件的契约错误。

证据：[apps/desktop/src/exports.ts:12](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/exports.ts#L12)、[apps/desktop/src/exports.ts:37](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/exports.ts#L37)；[packages/toutiao/src/workbench/data.ts:52](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/toutiao/src/workbench/data.ts#L52)；[packages/toutiao/skill/templates/交稿单-图文.md:23](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/toutiao/skill/templates/交稿单-图文.md#L23)。

最小修正：导出从实际当前稿读取完整内容，用当前元数据确定标题；按项目已有标记格式清理，统一处理正文已有标题。预览可以截断，正式导出不能直接复用截断文本。发布残留检查也应检查最终输出，而不只检查清理前文本。

## R6 · 作品租约的重新打开和释放路径不完整

**影响一：关闭另一个宿主后，选择菜单重新打开当前只读作品，界面仍可能一直只读。** selectSnapshot 对同一 scope 直接返回，不再调用 api.select，也不刷新 access。界面所提示的“关闭另一应用后重新打开即可写入”在这条操作路径上无法兑现；切到别的作品再回来才会触发重新认领。此项为源码控制流结论。

**影响二：通过符号链接路径打开的租约不能按同一路径正常释放。** claimWorkspace 用 realpath 作为 held 的键，releaseWorkspace 却用 path.resolve 查找。定点复现结果为 `aliasLeaseRemainsAfterRelease=true`；直到统一释放或退出进程才清掉这把锁。Linux 上已复现，未另做 Windows junction 实机复现。

证据：[apps/desktop/src/client.jsx:144](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/client.jsx#L144)；[apps/desktop/src/main.ts:204](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/main.ts#L204)；[packages/core/src/workspace-lock.ts:54](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/core/src/workspace-lock.ts#L54)、[packages/core/src/workspace-lock.ts:99](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/packages/core/src/workspace-lock.ts#L99)。

最小修正：同一作品的显式重新打开也经过租约刷新，并统一认领和释放所使用的规范路径。继续使用现有锁文件和进程生命周期，不增加新的租约服务。

## R7 · 未保存的方法编辑会在作品或结果跳转时丢失

**影响：作者修改用户方案但尚未保存，切换作品或点击结果卡跳转后，编辑草稿可直接丢失。**

保留 MethodsPane 的挂载已经解决了“只切右栏标签”时的丢失，但外层 Workspace 会在作品变化或 workspaceKey 改变时重新挂载。canLeave 只检查 focused.current.dirty，即段落编辑状态；方法草稿的 dirty 仍封闭在 ProfilesDialog 内。原对话框的 close 检查在 inline 模式的外层跳转中没有被调用。

最小修正：把方法面板未保存状态接到现有的离开检查，或让现有工作区在这些跳转中保留该编辑状态。无需为所有表单新建一套状态框架。本项由组件生命周期和状态来源确认，未进行鼠标操作录屏复现。

## R8 · null 配置会绕过恢复默认值的启动逻辑

**影响：配置已经无法使用时，应用退出，未达到计划 A2“默认启动并提示”的要求。**

当前 json 帮助函数只处理读文件及 JSON.parse 的异常。合法 JSON `null` 会成功返回，随后的 ui.workspace、stored.writer、search.secret 解引用在恢复逻辑之外抛出；main 的启动异常处理会弹错误后退出。writer.json 的 raw.toutiao 也有同类入口。

当前 Settings 源码的定点复现：desktop.json、model.json、search.json 分别写入 null，三个独立场景均未完成 load，分别报告读取 workspace、writer、secret 的 TypeError。没有读取或使用任何真实凭据。

证据：[apps/desktop/src/settings.ts:29](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/settings.ts#L29)、[apps/desktop/src/settings.ts:38](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/settings.ts#L38)；[apps/desktop/src/main.ts:421](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/main.ts#L421)、[apps/desktop/src/main.ts:784](https://github.com/ouzx6696-cmyk/dsh-zhizhang/blob/253305d5299ebf966b2d91344ca1d37110df124e/apps/desktop/src/main.ts#L784)。

最小修正：在配置读取入口区分“可用的配置对象”和 null／数组等错误形状，沿用已有默认值与 notice。范围只限本版承诺恢复的配置文件，不需要通用容错框架。
