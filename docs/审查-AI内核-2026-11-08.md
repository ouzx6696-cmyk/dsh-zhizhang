## 一、总体评价

T22 和本轮改造之后，内核的骨架是对的，而且好看：

- 每个阶段是一次无工具、无历史的新请求，提示词由代码拼装。
- 阶段输出先由代码校验，再落入 journal；交付靠 marker 和版本号做到幂等。
- 阶段卡按方法原文 sha256 全局缓存。
- 所有模型输出都被当成“数据”，不信任。

这套“编排归代码”的路线，比 DeepWrite 那种以对话 agent 为主、靠工具提交的写法**更可控，也更容易恢复**。

短板集中在三处：

1. **缓存只做对了一半**：前缀顺序排好了，但请求结构让 Claude 系的缓存断点吃不到，可选块的取舍也会让前缀在阶段间漂移。
2. **调用结构偏贵**：两两擂台 24 票、修订输出全文、来源原文每阶段重发。
3. **运行时细节粗糙**：三层重试叠加、截断照样重试且用量丢失、journal 并发写有竞态、每阶段全量重读并序列化作品。

DeepWrite 在“调用一次模型”这一层更成熟：

- 用 pi-ai 自带的可重试分类器，关掉 SDK 自身的重试。
- 有空闲超时，截断后提示补交并带上原因。
- 有 sessionId 路由，还有 FIFO 并发闸。
- 多稿评估是一次调用看全部候选。

织章在“流水线与恢复”这一层更强。

| 维度 | 织章 | DeepWrite（仅据所读模块） | 一句理由 |

## 二、问题清单（按收益/风险排序）

记号：收益是估算，没有实测。规模 S 约 ≤50 行，M 为 50–200 行，L 为 >200 行或涉及 UI/设置。

### P0：高收益，低风险

**#1 整包是一条 user 消息，Claude 系缓存前缀命中不了**
- 位置：`apps/desktop/src/workflow/run.ts:60-81`、`apps/desktop/src/workflow/stage-model.ts:83-93`
- 问题：pi-ai 在 Anthropic 接口和 OpenRouter 的 anthropic 兼容格式下，只在 **system** 和**最后一条消息的最后一个块**上打 `cache_control`（见 `node_modules/@earendil-works/pi-ai/dist/api/anthropic-messages.js:920-955,1216-1235`、`openai-completions.js:799-810`）。整包放在一个 text 块里，唯一的断点在包尾，只有整包完全相同才会命中，所以本轮“共享前缀”的排序在这类服务上一分钱都省不下来。同时也没传 `sessionId`，OpenAI 的 `prompt_cache_key` 用不上。
- 改法：`contextPacket` 同时返回 `prefix`（职责、本书设定、材料）和 `suffix`（方法、输入、要求、格式）。`completeSimple({ systemPrompt: prefix, messages: [{role:"user", content: suffix}] }, { sessionId: runId })`。按前缀自动缓存的服务（DeepSeek 等）行为不变。
- 收益：Claude 系每个任务第 2 个阶段起，前缀（常占包体 40–60%）按缓存读价计费。
- 规模：S

**#2 可选材料在每个阶段各自取舍，前缀漂移**
- 位置：`packages/core/src/workflow.ts:145-165`（contextPacket）、`run.ts:53-81`
- 问题：可选块是逐个试放的，放得下就收，放不下就跳过，后面更小的块照样能收。可变部分的大小每阶段不同：场景阶段很小，审读阶段带整章正文。于是同一任务里，“本卷规划”可能这一阶段在、下一阶段不在，从第一个不同的块开始前缀就断了。长书和大输入阶段最明显。
- 改法（二选一）：
  - (a) 每个任务只决定一次材料取舍：构造 `WorkflowRun` 时按 `limit × 0.5` 选定，冻结后复用；单阶段超限时只去掉末尾的块。
  - (b) 取舍改成“前缀稳定”：遇到第一个放不下的可选块就停，后面的都不收。
- 收益：同一任务各阶段的前缀字节完全一致，#1 的效果才稳定。
- 规模：S

**#3 读者投票的输入把 persona 放在最前，另外用的是编辑方法卡**
- 位置：`apps/desktop/src/workflow/editor.ts:46-58`、`chapter.ts:142`、`article.ts:211`
- 问题：
  - 输入是 `{persona, A, B}`，同一挑战者的 6 票从 persona 开始就分叉，两篇正文（约 8–10k token）每票都按未命中计价。
  - `card` 传的是 `edit`（番茄）或 `s5-editing`（头条）阶段卡，读者拿到的是编辑规则，角色混淆，每票还多出约 1.5–2.5k 字。
- 改法：
  - 输入改为 `{A, B, persona}`。
  - 换成固定的短读者卡（常量，几行）。
  - 发射顺序先跑两种位置各一票（预热两个前缀），其余 4 票再并发。
- 收益：标准档黄金章读者比较约 29 万输入 token 里，约 14 万从未命中转为命中（DeepSeek 一类自动前缀缓存）；每票还少 1.5–2.5k 字方法卡。代价是选稿多一个往返的时延。
- 规模：S

**#4 头条来源原文（最多 48000 字）在每个阶段的“本阶段输入”里重复**
- 位置：`article.ts:134`（article-card）、`:150`（headlines）、`:171`（blueprint）、`:189-195`（每份草稿）、`:232`（facts-revise）、`:281`（qa-revise）、`article-facts.ts:13-19`（facts、facts-1）
- 问题：source 放在方法卡之后，每个阶段的方法卡都不同，所以 source 永远落在缓存前缀之外。资讯稿一次任务约 9–11 次调用带着同一份来源。
- 改法：`sources` 步骤之后构造 `material = [...run.context.material, {name:"来源原文", text: attribution+"\n"+text, required:true}]`，所有头条阶段传 `{ material }`，输入里只留 `sourceRef: "见材料：来源原文"`。
- 收益：来源 1 万字时，大约 9 万 token 改按缓存价计（估算）。
- 规模：S

**#5 三层重试叠加，而且分类靠正则**
- 位置：`stage-model.ts:7-16,36-56,83-93`、`packages/core/src/workflow.ts:173-208`
- 问题：
  - `completeSimple` 没传 `maxRetries`，OpenAI 和 Anthropic 的 SDK 默认自己重试 2 次。
  - 外面一层 `withProviderRetry` 再试 3 次。
  - journal 默认 `retries=1`，对“退避用尽后的 transient 错误”又整轮重来。
  - 一次阶段最坏是 3×4×2 = 24 次 HTTP。
  - 分类用 `\b429\b` 一类正则去匹配消息文本，不认识 `quota exceeded`、`billing`；而 pi-ai 1.4.0 已经导出了 `isRetryableAssistantError(message)`（`utils/retry.d.ts:57`），里面有区分“额度耗尽，不可重试”的列表。
- 改法：
  - `completeSimple` 传 `maxRetries: 0`。
  - `stopReason==="error"` 时先用 `isRetryableAssistantError(answer)` 判断，抛带 `kind` 的 `StageError`。
  - 余额正则保留，并补上 pi-ai 的额度词。
  - journal 层不再重试 transient 和 provider 类错误，只重试内容错误。
  - 退避加 ±20% 抖动。
- 收益：限流时不再雪崩式重发；额度耗尽时 1 次请求就暂停。
- 规模：S

**#6 截断（`stopReason==="length"`）照样重试，用量也丢了**
- 位置：`stage-model.ts:94-111`、`workflow.ts:180-205`
- 问题：
  - 截断是确定性失败：同一个包、同一个 maxTokens 再发一次，大概率还是截断。可 journal 会照样重试一次，等于把整份最大输出再烧一遍。
  - 抛错发生在 `return { usage }` 之前，这次调用最贵的输出 token **既不进 journal 用量，也不进预算**。
- 改法：
  - `StageError` 带上 `usage`；journal 的 catch 里把 `error.usage` 累加进 `row.usage`。
  - `kind:"truncated"` 不重试，直接失败。也可以只对非正文阶段重试一次，并附上“上次被截断，请压缩”。
- 收益：截断时少烧一整份最大输出；用量和费用显示真实。
- 规模：S

**#7 内容校验失败后，重试发的是完全相同的包**
- 位置：`workflow.ts:173-181`、`run.ts:44-88`
- 问题：重试不带上一次的失败原因（JSON 结构不对、篇幅不对、引文不在原文、规则编号缺失……），同一模型在相近温度下往往再错一次。DeepWrite 的思路是截断或漏交之后，补一条带原因的提示。
- 改法：`step` 的 `execute` 接收 `{ attempt, lastError }`；`run.model` 在 `lastError` 存在时，于包尾追加 `## 上次返回未通过校验\n{lastError}；请按返回格式完整重答`。追加在包尾，不影响前缀缓存。
- 收益：内容重试的成功率明显上升（定性判断）；同类失败少烧一轮。
- 规模：S

**#8 journal 并发 save 有竞态，而且每次都全量 fsync、克隆、走 IPC**
- 位置：`packages/core/src/workflow.ts:142-146`；并发来源是 `chapter.ts:111`（起稿 3 路）、`editor.ts:46`（投票 4 路）
- 问题：
  - `save()` 每次用随机临时文件名，经 `atomicWrite` 写入、fsync，再 rename。几路并发时，先 stringify 的旧快照可能后 rename，覆盖掉较新的快照。崩溃后已完成的阶段会被当成未完成，重新花钱。
  - 每个阶段至少 save 两次；每次都写缩进 JSON 加 fsync，还要 `structuredClone` 整个 record（里面有全部草稿）、经 IPC 推给渲染进程。
- 改法：save 串行化并合并：in-flight 期间来的多次 save 合并成一次写，写的时候再 stringify 最新状态（代码见第三节 E）。publish 可以节流到 ≥200ms，终态立即推。
- 收益：消除旧快照覆盖新快照；黄金章写盘次数约减半，IPC 负载下降。
- 规模：S

**#9 并发阶段同时过预算预检，可能超支**
- 位置：`run.ts:82-87`
- 问题：`used` 只累计**已完成**阶段的用量。4 路投票同时预检时，看到的是同一个 `used`。另外 `limit` 的输出预留只有 `contextWindow - maxTokens - 1024`，没有安全余量；DW 的做法是预留 `min(maxOutput, 32k, 窗口 25%)` 再加一段余量。
- 改法：`WorkflowRun` 维护 `inflight`，预检时把 `used + inflight + estimate` 一起算，发出前预留，结束后释放（代码见第三节 E）。
- 收益：预算闸真正是“阶段边界”，不会超出一批并发。
- 规模：S

**#10 每个阶段前，assertCurrent 都全量重读并序列化作品**
- 位置：`context.ts:119-127`（assertIdentity）、`:195-211`（snapshot）、`:236-266`（assertCurrent）；调用点 `run.ts:46`
- 问题：
  - 每个阶段都要重新读：作者偏好、4 份方法（每份还要解析一次 profile）、meta、本章、前章、伏笔、知情、连续性账本。
  - 读完拼一个大对象做 `JSON.stringify`，再和 basis 字符串比较。黄金章约 35 次，并发投票时 4 份同时跑；长书的账本有上万条，这些都压在 Electron **主进程**。
  - `snapshot()` 与 `assertCurrent` 把同一个对象结构写了两遍；`JSON.parse(snapshot())` 又做了一次无意义的往返。
- 改法：
  - 抽一个 `fingerprint()`，构建和校验共用，比较 sha256。
  - `WorkflowRun` 内部用 2 秒节流共享一次检查，同一批并发阶段只检查一次。交付前仍然逐次严格检查，那里本来就自己调用。
- 收益：主进程 IO 和序列化大约降到原来的 1/4～1/10，UI 卡顿风险下降。
- 规模：S

**#11 每个阶段都重建 ModelRuntime**
- 位置：`stage-model.ts:77-81` 调用 `session/pi-adapter.ts:69-102`
- 问题：`ModelRuntime.create({refreshOnCreate:true})` 每次都会读 auth、构建全部内置 provider 目录并做一次离线 refresh（`pi-coding-agent/dist/core/model-runtime.js:79-117`），每个阶段一次，并发时多份同时跑。
- 改法：按 `sha256(authPath, role, settings)` 记住 Promise，失败就删掉；设置保存或 reconfigure 时清空。
- 收益：每阶段少一次目录构建（耗时没有实测）。
- 规模：S

**#12 `host.key()` 每次都同步 realpath**
- 位置：`session/manager.ts:101-110` 调用 `packages/core/src/identity.ts:5-17`（`realpathSync.native`）；热点是 `service.ts:78-82`（每次 publish 都调）
- 改法：按 `mode\0root\0work\0article` 记住结果。
- 收益：热路径去掉同步 IO。
- 规模：S

**#13 自动记账抢走 `current` 指针，暂停的章节任务无法恢复**
- 位置：`session/manager.ts:176-192`（定稿后自动 `start({kind:"ledger"})`）、`service.ts:137`（无条件写指针）、`service.ts:60-77`（resume 只读指针）
- 问题：章节任务因预算或余额暂停以后，作者去定稿别的章节，记账任务就会覆盖同一作品的 `current`，暂停的任务从“恢复”入口消失，只剩在历史里。何况记账改了 `writer-continuity.json`，而它在章节任务的 basis 里，就算找回指针，恢复也会报“依据已改变”（见 #14）。
- 改法（本轮）：指针所指的任务处于 paused 时，记账任务不写指针。更稳妥的做法是暂停期间不自动记账，提示作者，并把待记账章节写进 `pending-ledger.json`，等那个任务结束后补跑。
- 收益：修掉一个会丢进度的真实路径。
- 规模：S（不写指针）/ M（排队）

### P1：高收益，中等风险或中等规模

**#14 basis 过宽，而且整段塞进 journal 反复写盘**
- 位置：`context.ts:195-211`、`workflow.ts:52-56,144`、`recovery.ts:19-20`、`book.ts:8`
- 问题：
  - 章节任务的 basis 包括整本书的 foundation、planning、全部伏笔与知情、整个连续性账本。任何无关改动，比如别章的记账、加一条人物，都会让任务中途失败或无法恢复。
  - 这个可能上百 KB 的字符串还存在 record 里，随每次 save 写盘和推送。
  - `book.ts` 直接 `JSON.parse(basis)` 去拿章节列表，耦合到 basis 的内部结构。
- 改法：
  - basis 改为“本任务实际读到的东西”的指纹：stable 加 material 各块的哈希，再加本章和前章的 revision。
  - 全文快照写到旁路文件 `run-xxx.basis.json`，只写一次，recovery 用。
  - record 里只留哈希。
  - `bookPipeline` 改从 context 拿 `existingIds`。
- 收益：可恢复率上升；journal 体积下降一个数量级。
- 规模：M

**#15 恢复时，用上下文相关的校验器去重解析已完成的输出**
- 位置：`workflow.ts:157`（`return parse(row.output)`）；例子是 `article.ts:197-203`（recentTitles 是运行时取的）、`chapter.ts:121-129`
- 问题：已完成阶段的输出在恢复时会被 parse 重新校验，而 parse 闭包依赖“当前”的外部状态，比如近期标题。外部一变，已完成的阶段就会永久抛错，任务无法恢复。
- 改法：parse 拆成 `decode`（只管结构，纯函数，恢复时使用）和 `accept`（含上下文校验，只在新生成时使用）。`step(id, title, decode, execute, signal, retries, accept?)`。
- 规模：S–M

**#16 选稿结构：两两擂台改为整体排序**
- 位置：`editor.ts:29-101`
- 问题：
  - 标准档黄金章 5 稿要打 4 个擂台，每台 3 画像 × 2 位置，共 24 票，4 个擂台**串行**。
  - 精品档 8 稿 5 画像要 70 票。
  - 一共读了 48 份或 140 份正文。
- 改法：
  - 每个画像一次调用，看全部候选并给出排名与弃读点，正序、倒序各一次，用 Borda 计分。标准档 6 次，精品档 10 次。
  - 可选：前两名再做一轮两两比较，2 画像 × 2 位置。
  - 若配合 #3 把 persona 放到最后，正序和倒序两个前缀可以被各画像共享。
- 收益（估算）：调用数 −75%/−86%；正文读取量 −37%/−43%；选稿时延从 4 轮串行降到 1 轮。
- 风险：长上下文同时比较 5–8 稿的判别力。建议用假模型和小样本人工对照后再开。
- 规模：M

**#17 定向修订、删改事实、质检精修都要求输出全文**
- 位置：`editor.ts:153-167`、`schema.ts:216-222`、`article.ts:227-237,276-286`
- 问题：
  - 改 1–5 处硬伤，却让模型重写 3000–6000 字全文，输出 token 是输入的 2–4 倍价。
  - 必须事后再用 `revisionScope` 防范模型“顺手改了别处”。
- 改法：
  - 返回改为 `{"edits":[{"quote":"原文","replacement":"新文","issue":1}]}`，代码用 `locate` 定位后替换。范围检查就变成“每条 quote 都必须在允许的段落里”。
  - 失败时退回到全文重写。
- 收益：修订类阶段的输出 token 降 80–90%（估算），范围保护天然成立。
- 规模：M

**#18 方法依赖没注入：`s4-news`/`s4-story` 要求先读 `s4-common`；`write-chapter` 让写手“按需读 rhythm/scene/prose”**
- 位置：`workflow/methods.ts:20-31,77-95`；方法文本 `packages/toutiao/profiles/default/s4-news.md:3,49`、`s4-story.md:3`、`packages/fanqie/profiles/default/write-chapter.md:15`
- 问题：
  - 流水线阶段没有工具，不能“按需再读”。
  - 头条起稿和精修完全看不到 `s4-common`（延伸的接法就在里面），方法送达有缺口。
  - `methodBasis` 也没把 `s4-common` 算进指纹。

- 收益：属于质量问题（写手少一半规则）。
- 规模：S–M

**#19 阶段级的思考强度与模型分档**
- 位置：`stage-model.ts:88-92`（`reasoning` 跟着角色走）
- 问题：投票、场景、标题矩阵、事实链、记账抽取、阶段卡压缩都用角色的 thinkingLevel。如果作者给评审开了 high，24 票每票都会产生大量推理 token。
- 改法：`run.model` 的 options 加 `effort?: "low"|"inherit"`，对投票、场景、标题、阶段卡用 `clampThinkingLevel(model, "low")`。设置里可以再加一个“轻量”档模型，缺省回落到 editor。
- 收益：推理模型下，比较类阶段的输出 token 大幅下降（没有实测）。
- 规模：S（effort）/ L（新档位要改 UI 和设置）

**#20 没有空闲超时，也没有流式进度**
- 位置：`stage-model.ts:83-93`
- 问题：连接挂住时要等到 SDK 默认的 10 分钟超时；起稿要几分钟，面板只显示“起稿 2/5”。
- 改法：
  - 先传 `timeoutMs`，比如正文阶段 6 分钟、其他 3 分钟。
  - 再改用 `streamSimple`，每 1–2 秒 publish 一次已收字数，同时做空闲看门狗：90 秒没有新事件就 abort 当前请求，按 transient 处理。
- 规模：S（timeoutMs）/ M（流式）

**#21 头条 final-review 常常在重审同一份正文**
- 位置：`article.ts:288-297`
- 问题：质检第 0 轮就通过、也没有删改事实时，`checked.draft` 与 `editDraft` 最后一次审读的正文完全相同，final-review 是重复的。
- 改法：记录最后一次审读的 `bodyHash`；终稿哈希相同就直接复用那份报告。
- 收益：常见路径每篇少 1 次 editor 调用（约 1 万 token）。
- 规模：S

**#22 任务池不会快速失败，投票失败的处理还前后矛盾**
- 位置：`session/task-pool.ts:6-27`、`editor.ts:66-67` 对比 `:71-80`、`chapter.ts:133-136`
- 问题：
  - 一稿因预算暂停或 abort 失败后，其余几路照样跑完，钱花了，最后整单还是抛错。
  - 投票这边先 `throw failed.error`，后面又写了 `outcome.status === "ok" ? … : undefined` 的容错分支，这个分支是死代码。
- 改法：

  - 投票只对 abort 和 WorkflowBudgetError 整单失败，单票内容失败按“不计票”处理。
- 规模：S

**#23 没有全局 provider 并发闸**
- 位置：`chapter.ts:25`、`editor.ts:24`、`article.ts:183`（头条按稿数全并发）
- 问题：两部作品同时跑，或流水线和对话并行时，同一 provider 的并发数会相加，更容易撞上 429，退避又把时延拉长。
- 改法：在 `stage-model` 层加一个按 `provider+baseUrl` 计的 FIFO 限流器（默认 4），流水线内部的池只决定顺序。
- 规模：S–M

## 四、与 DeepWrite 对照得到的设计启发（只借思路）

| 主题 | DeepWrite 的做法（概括） | 对织章的启发 |
|---|---|---|
| 重试 | 关掉 SDK 自身重试，统一用 pi-ai 的可重试分类器，退避带抖动 | 对应 D 和 #5 |
| 截断与漏交 | 同一会话内追加一条带原因的补交提示，限 2 次 | 对应 #7（无会话版：包尾追加失败原因） |
| 超时 | 模型请求有空闲看门狗（默认 5 分钟），超时按可恢复错误处理 | 对应 #20 |
| 缓存与路由 | system 与对话分开；每个会话稳定的 sessionId 跨轮、跨重试 | 对应 A |
| 预算 | 输出预留取 `min(最大输出, 32k, 窗口 25%)` 再加安全余量；token 估算按非 ASCII 加权 | 对应 #9、#26 |
| 多稿评估 | 一次评估调用看全部候选（有总字数上限），输出选择和理由 | 对应 #16（织章可以保留正倒序和多画像，提高稳健性） |
| 并发 | FIFO 并发闸，放行的名额直接交给下一个等待者 | 对应 #23 |
| 契约 | 独立的 contracts 包承载跨层类型 | 对应 #30、#32 |

织章应当保持、DeepWrite 没有的长处：

- 阶段输出先由代码校验再落 journal；
- 交付 marker 与版本号的双重幂等；
- 阶段卡按方法哈希做全局缓存；
- “作者是最终裁判”的交付语义。

上面所有建议都没有动这几条。
