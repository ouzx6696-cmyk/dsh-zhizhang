# 番茄长篇模式

## 1. 结构
- 代码都在 `packages/fanqie`：引擎（`engine/`：作品存储、`fanqie_*` 创作工具链、硬规则）、写作层（forge 方法、章纲/旧账检查、编辑审读、门禁）、写作台接口（`workbench/`）。桌面按模式与角色在 `create.ts` 一并注册引擎与写作层工具，不经 writer_enable。
- 作品数据（根基、章纲、正文、候选、拆书库）只有一份，默认在 `<会话目录>/.writer/`。写作层直接用引擎的存储层与作品选择（`works.ts`）；落盘一律走引擎工具。编辑审读回报是写作层自己的文件，存在作品目录 `writer-reviews/<章 id>/`。
- forge 三件套（inspiration-forge 规划、inspiration-forge-library 拆书、novel-writer 写作与编辑）原文放在 `packages/fanqie/skill/forge/`，**一字未改**。
- 原文里的落盘指令（自有目录、init_project.py、archive_draft.py）在取用时由 `fanqie_method_get`（`原版:id` 读原件）前置的对照表改道到引擎工具。这样原文可以随上游升级整体替换。
- forge 的五个检查脚本通过 `fanqie_bridge.py` 包成统一 JSON 契约；脚本本身不改，同输入同输出。
- 例外：`novel-writer/scripts/manuscript_linter.py` 里的 `scan_style`、`utf16_positions` 是本仓在上游 forge 之外新增的，供 `fanqie_bridge.py style` 给桌面端返回按 UTF-16 计的命中坐标；上游原有函数未改。

## 2. 字段映射
引擎章纲与 forge 章纲接口（check_outline.py 的 BLOCKS / FIELDS）一一对应：

| 引擎 outline 字段 | forge 章纲 | 检查 |
|---|---|---|
| synopsis | 1. 剧情梗概 | 非空、无显式占位 |
| conflict | 2. 核心冲突与看点 | 同上 |
| beats | 3. 情节推进节点 | 同上 |
| ending | 4. 章末落点 | 同上 |
| pov | 视角 | 同上 |
| targetWords | 目标篇幅 | >0；番茄常见区间 1500–6000 字外只提示 |
| locks | 锁定事实 | 同上 |
| knowledge | 人物知识边界 | 同上 |
| situationLens / livedScene / stateLens | （引擎独有：处境透镜、亲历重心、状态透镜） | 不检查，由引擎自己的 brief 约束 |

forge 的"节奏档位"在引擎里对应作品级 `pace`（`fanqie_foundation_set` 的 pace 参数），本插件不另设字段。

## 3. 正文体检合并（ADR）
- **决定**：合并为一个入口 `fanqie_style_lint`。引擎语感雷达照旧给命中、签发 lintPassToken；其后附「forge 正文体检」（manuscript_linter：超长段、七类套话，台词命中只计数）。与雷达已命中片段重叠的套话不重复列出。
- **理由**：两边各报一遍会重复提示；放进同一个工具后一次看全。规则本身都不改，命中仍只是"值得回看的位置"。
- **实现**：`engine/tools/audit.ts` 的 style_lint 经 `engine/ports/audit.ts`（StyleLinterPort）把「forge 正文体检」段追加到雷达输出；追加文本不影响雷达命中数与 lintPassToken；Python 不可用时只附一行"追加体检暂不可用"。

## 4. 编辑子代理
- 主写手通过桌面独立编辑任务发起审读；编辑使用独立 PI 会话和受限工具集。
- 编辑能读、能出**编辑候选**（`fanqie_candidate_edit_brief/stage`），不能采纳、定稿、改根基或章纲、入库。
- 回报固定走 `fanqie_review_report`：结论、四类硬伤（关键剧情与落点、本书硬约束、人物认知、正文接续）、L1–L3 定位、是否完整回读、实际改动范围。回报绑定正文 SHA-256（首尾换行归一），正文一改即过期。存在作品目录 `writer-reviews/<章 id>/<时间>.json`。

## 5. 定稿门禁
- `fanqie_chapter_save status=final` → 作者确认；任何 `force=true` → 作者确认。都锁定不可关。
- `fanqie.requireEditorPass: true` 时，定稿前还须有"通过"且与当前（或本次提交的）正文版本匹配的审读回报。条件实现在 `review.ts finalizeProblem`，工具定稿（`chapter-save.ts`）与写作台定稿共用同一处，不是门禁 id。
- 审读通过不自动获得定稿权：门禁顺序是先查审读、再请作者确认。

## 6. 引擎与写作层的衔接
引擎（`engine/`）与写作层同在 `packages/fanqie`，直接调用，不经钩子：
| 位置 | 调用 |
|---|---|
| `fanqie_chapter_save status=final`（engine/tools/works.ts）与写作台 `POST /chapter/finalize` | `review.ts finalizeProblem`：requireEditorPass 时要当前正文的"通过"回报 |
| 写作台读单章 `GET /chapter` | `review.ts chapterReviewInfo`：最新回报摘要、是否过期、定稿条件 |
| `fanqie_style_lint` 三种扫描（engine/tools/audit.ts） | `engine/ports/audit.ts` StyleLinterPort：forge manuscript_linter，去掉与语感雷达重复的命中后追加 |
| 引擎解析数据根（engine/work-store.ts ensureStorage） | 会话目录 `current` 指针（`create.ts` 读写）：主会话最近一次会话文件（子代理不写） |

启用：桌面按模式装配（`create.ts`）：`engineTools` 与 `createFanqieTools` 一并注册，补充规则与门禁同处装配。

## 7. 写作台投递
- 番茄长篇三种动作：`continue`（续写下一章：按章序第一章还没正文的；都写过就是新的一章）、`review`（派编辑审读本章）、`revise`（按最新回报修改）。
- 今日头条四种动作：`new`（新写一篇，附言当题材）、`continue`（按当前状态推进下一步）、`review`（派编辑红笔并质检）、`revise`（按最近质检与编辑意见修改）。
- 作者附言 ≤300 字原样附在末尾。发出的是普通用户消息，以【写作台】开头，mode=queue（Agent 忙时排队，不打断）；requestId 由写作台生成，桌面主进程据此对重复投递去重。
- 目标会话：最近在该数据目录（长篇按引擎数据根，头条按头条数据目录）调用过写作工具的主会话。没有会话时按钮置灰并写明原因。
- 未做：模型深度调用；按作品而非按数据目录区分会话。


## 拆书库：存在哪里、拆多深、如何使用

统一写作根为 `D:/写作` 时，默认作品在 `D:/写作/novels`，项目状态在 `D:/写作/.writer`，拆书库在 `D:/写作/.writer/library`。导入旧项目时默认位于该项目数据根的 `library`；`libraryRoot` 可以覆盖位置，因此不要仅按目录名字判断库是否丢失。库中 sources 保存书源，cards 保存已采纳卡，candidates 保存候选，analyses 保存阅读分析，index.json 是索引。不要手动删除索引或直接搬动部分子目录。

拆书的终点是解决一个创作问题，不是把每本书拆成越多卡越好：

| 目标 | 建议范围 | 可以交付什么 |
|---|---|---|
| 某段为什么有效 | 完整场面及必要前后文 | 有出处的机制说明、迁移条件和失败边界，不必入库 |
| 学开篇 | 从故事承诺到首次实际回报的小单元 | 期待怎样建立、行动怎样兑现、章末怎样接续 |
| 学全书结构 | 测绘后读关键转折和前因后果 | 抽样假设；不能冒充全书结论 |
| 完整拆解 | 明确范围后按授权全量阅读 | 阅读范围与证据完整的报告及少量可复用卡 |

Auto 默认约 10% 分层抽样；Full 需要确认成本。目录扫描、正文已读、深读和未读必须分开。连续批次没有新机制、不能改变当前创作选择时，应说明增量低和未解问题，建议停止或收窄；不能把停止说成整书已读。

正式入库路线：交书 → 抽样计划 → 分批读原文 → 章节事实 → 结构聚合 → 候选卡 → 显式采纳 → 报告 → 按需组包。局部拆解可以直接用 reference_analyze，不必跑九步。

### 如何真正用上

在 Agent 中可以直接说：

> 从拆书库查找“信息差、对手合理回应”相关卡，先读卡片全文与失效条件，选适合本书的少量卡用于第三章简报；保留本书人物、规则与既有事实，没有合适卡就直接按章纲写。

模型应执行 library_search → library_card_get，再把选定的 card_ids 显式传给 chapter_brief。开书与规划则传给 inspire_start。combo_suggest 可以按来源和主题推荐组合，但排序不是文学质量评分，推荐不等于采用。lean 章节简报只使用 craft 卡，全书/卷幕机制应先落实到本书规划，而非期待每章自动注入。

库是项目级参考资产：同项目的作品可以复用；跨项目默认不会自动共享。入库不会训练模型，也不会自动覆盖方法方案或本书事实。当前软件尚无完整的“每张卡在何书何章用过、效果如何”的自动追踪，应在规划与审读中记录实际迁移和失效。

### 方法论与软件的边界

| 材料 | 职责 | 当前软件入口 |
|---|---|---|
| 默认/原版/用户方法方案 | 怎样规划、写作、编辑 | fanqie_method_get 按任务读取；用户方案可以覆盖 |
| 拆书卡 | 有证据的参考机制 | 检索、读卡、显式 card_ids 传递 |
| 本书根基、规划、章纲 | 当前创作约束与安排 | 对应作品工具落盘 |
| 当前正文、审读和版本 | 已写内容与作者决定 | 候选、采纳、审读、定稿及修订流程 |

两者大体匹配，但不存在“完美匹配”：上游方法的自有目录、初始化和归档脚本须换成客户端工具；工具校验只能核版本、字段与字面证据，不能证明文学效果、事实真实性或参考未造成结构照搬。规则扫描不是审读，独立编辑不是作者授权。软件发布采用本地假模型与自动化回归验收。

## RC2 整理与后续验证

本轮收口草稿离开保护、锁占用登记互斥、配置更新期间任务接收、CI 信号失败和 RC/稳定发行隔离；库批量读卡限制并发。默认方法补充拆书停止条件、实际调用和三类材料职责，清单与来源登记同步维护。

性能评估应使用含大量章节、历史修订、候选、拆书卡和长会话的代表性工作区，分别测首次打开、缓存刷新、切换、保存和输入响应。入口 JS 体积下降不能代替整机性能结果。本轮未升级 PI SDK；其 minimatch 中危依赖需单独评估兼容性后处理。

发行由自动化业务回归、Windows 原子写回归、安装器与便携包构建检查验收。崩溃遗留的 `.writer-workspace-claim` 登记锁已可自愈：登记写入持有进程 pid，桌面启动遇死 pid 自动清理并写 `workspace_claim_cleaned` 日志，活进程持有照常报占用。


调用补充：章节参考解析有明确优先级——本次显式 `card_ids` → 通过 `inspire_accept(apply=true)` 已绑定到本作品的卡 → 不使用卡。绑定后可在后续章节简报复用，无须每次重新传 ID；仅做 library_card_accept 入库不会建立作品绑定。lean 仍只取 craft，且受简报数量与长度限制，不是整库注入。更换本章参考时显式传入所选 ID，并核对简报回执中的实际来源。


## 桌面融合入口与持久化

“设置 → 资源与备份 → 本地拆书库”显示本次实际解析的库路径，可打开库文件夹或导入 TXT/Markdown 原文。不需要模型 Key 即可导入；导入只保存书源副本，不自动阅读、拆解、入库卡或开始付费任务。回执中的书名和书源标识可交给 Agent 指定分析范围。

正式拆书库需要本地持久目录，默认自动跟随项目，无须另填硬编码路径。导入来源可以是任意作者选择的 TXT/Markdown，也可由工具传入文本；入库后读取库内副本，原文件移动或删除不影响已导入资料。可用 libraryRoot 指定共享库，sourceRoot 仅作为导入时的书源查找目录，两者不是一回事。不同项目只有显式配置同一 libraryRoot 才共享卡；作品绑定仍由各项目维护。

迁移时先停止任务并处理未完成写入，再搬完整库（来源、索引、卡、分析等），同时保留项目 inspiration 下的作品绑定。外置共享库需单独备份；不能只备份 novels 正文，也不要认为作品备份按钮必然包含所有外置资料。当前没有自动搬库或合并多库功能。

长篇创作任务现在按意图实际读取当前方法方案：写章、修订、审读、根基/结构/章纲规划或拆书；用户覆盖优先。任务中携带方法正文及哈希，上下文面板可以核对加载凭据。普通状态查看不自动加载创作方法；其他专项仍按需调用工具。正文任务的精简交接也携带实际选中参考卡的内容，lean 不注入的规划卡不会记成已注入卡。哈希只证明所附版本，不证明模型已理解或执行。
