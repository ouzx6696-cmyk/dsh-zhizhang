# 0.9.5 迭代计划：运行逻辑收敛与精简

日期：2026-11-02（香港时间）。基线为 0.9.4 / `eabd87a`。需求依据：[完整审核与运行体系](0.9.4-RUNTIME-AUDIT.md)。

本计划是待实施要求，以下验收项当前均未因计划完成而视为通过。开发主线继续为内置 PI、自有写作内核与客户端。

## 1. 目标与范围

0.9.5 完成三件事：修复已经确认的状态与语义错误；收敛重复兜底、重复说明和重复执行；让少量检查覆盖真正会伤害作者数据或任务行为的风险。

保持作品格式、工具业务能力、方法方案和既有作者保护。技术取舍以清晰调用链、真实失败和低维护成本为准。版本范围不包含新 Agent 宿主适配、数据库迁移、插件化重建、全仓 TSX 改写、通用事务／事件／测试平台。

## 2. 开发规则

1. 按下面五批顺序推进；先修正确性，再精简支撑代码，最后冻结交付。
2. 每次删判断先说明它保护哪个输入或不变量；找不到实际调用条件的内部兜底优先删除，文件／模型／IPC 边界的验证保留。
3. 缺失、损坏、过期、无权限分别处理。正常空值只表达契约允许的“没有”，降级须带实际原因。
4. 业务内部保留明确输入和错误语义；外部格式转换在边界完成。沿改动路径补类型，不把 898 个 any 全部迁移作为发版条件。
5. 保留涉及作者数据保护的规则：版本、哈希、真实确认、写入互斥与恢复依据。不要用缩短代码交换数据风险。
6. 注释解释非显然的原因和约束。固定模板、开发历史与反复免责声明移出运行时热路径；不按注释百分比或代码行数做删减考核。
7. 只运行受影响的现有检查；最终候选做一次组合核对。失败或新修改影响结果时再重跑相关部分，文档修改不重跑模型与桌面全套。

## 3. 五批实施指导

### 第一批：修复目标提交和事实被兜底改写

**修改范围**：`main/targets.ts`，`ArticleStore.list / listArticles`，`activeProfile`，`session/create.ts`，`library/schema.ts` 与实际 cue 使用处。

**工作要求**：

- 目标切换收进一个局部流程，明确准备、提交和旧资源释放。复用已有串行机制或完成整个流程的代际管理，避免两套半完成的保护叠加。
- 新目标解析、访问获取或选择持久化失败时，旧目标和它的有效租约保持一致；只清理本次真实取得且不被其他任务使用的新资源。旧资源清理失败不能伪称新目标未提交。
- 正常文章继续显示；坏文章／坏根返回可定位的不可读状态，不静默跳过，不修补或覆盖原文件。
- 固定方法不存在或损坏时明确报告。非固定的旧选择允许按既有兼容规则回落，但须把原因交给调用方。
- current 指针只有明确缺失时才创建新会话；读取、权限及格式错误保留原记录并报告。
- humanFeel 缺失保持缺失。固定 failAsTemplate 可作为展示建议，不能作为卡片提供的 cue。旧卡兼容读取时也不把通用模板当显式场面依据，不批量改写作者卡片。
- 同类扫描针对当前读写链路扩展到 inspiration 索引、台账同步，按“可选降级带原因”处理；不要逐个 catch 一律删除。

**完成条件**：审核中的五类定向复现结果均被纠正；正常选择、正常文章、有效固定方案、已有真实 cue 的行为保留。检查在既有业务测试中复用临时目录与故障注入，不建新故障平台。

### 第二批：收敛会话角色、错误和编辑状态

**修改范围**：`session/prompt.ts / create.ts / tools.ts`、`host-generic`、长篇工具包装、桌面 controller、两个工作台 hook、已有编辑保护。

**工作要求**：

- 按 writer/editor/planner 分别组装提示；公共段只放共享事实。委派指令仅交给真正具备委派工具的角色，规划不继承完整写作／定稿路线。
- 业务失败在内部保持可判别语义，PI、HTTP 和旧兼容入口分别负责最终输出；逐步撤掉“异常转字符串 → exec.failure → 重新抛异常”的链路。保留外部既有工具格式，迁移聚焦当前链路。
- 为目标选择、采纳输入与结果、文章保存、方法选择、任务 Focus 明确类型。对这些接口，内部直接使用契约；不再遍布 `|| []`、`as any` 来猜形状。
- 源码、段落和方法编辑向现有离开决策报告同样的 dirty/saving 状态；局部编辑数据仍归编辑器所有，不新增全局草稿仓库。
- 长篇和头条都向发送快照报告实际 dirty。后台保存内容与未保存文本保持可区分。
- 普通切换、目录选择取消、应用关闭与更新安装使用一致的保存／离开含义。保存中阻止破坏性离开；取消目录对话框不丢草稿；更新安装不先销毁会话再发现保存未完成。

**完成条件**：三个角色的可执行指令与注册工具一致；失败没有字符串猜测或执行上下文暗传状态；四类离开动作沿相同规则判断，拒绝离开后文本与任务对象保持原样。

### 第三批：精简模型上下文、回执与重复刷新

**修改范围**：SYSTEM_BRIEF、客户端角色说明、Scheduler/采纳回执、工作台提示、`task-tracker` 与 controller 事件处理。

**工作要求**：

- 常驻规则只保留任务真正需要的模式、角色、版本、授权和材料边界；详细路径与原理按需由方法工具提供。
- 成功回执只交代实际保存对象／版本、当前有效告警和必要下一步。没有告警时不附固定解释段；真正的冲突、部分成功和损坏信息必须保留。
- 将“不是／不能／不代表”的泛化辩解改为具体动作。例如“当前版本未审读，请先读正文并交回报”；不要仅为缩字删除真实限制。
- 技术 Gate/Port 名称和策略说明保留在开发／方法信息中，作者界面用可直接行动的表达。
- 停止向 continuity 元数据新写固定 coverageNote；兼容读取已有字段，作者数据不批量迁移。
- 任务结束只由一个责任点触发工作台刷新，避免 agent_settled 和 refresh 各发一次。修正选中作品外事件的刷新范围；不新增事件总线、持久队列或复杂合并器。
- 在实际修改附近清理单纯转发、重复格式化和过期解释；大文件按职责处理本次涉及部分，不追求机械拆至指定行数。

**完成条件**：同一结束事件只有一次逻辑刷新；新旧输出对比中，固定重复段消失，实际结果和当前风险完整；默认值与说明不进入事实／诊断判断。模型调用次数和耗时有实际记录才写收益。

### 第四批：精简检查与构建体系

日常验证保留三个职责入口：核心业务、桌面行为、受影响的既有兼容。发行再做一次实际 Windows 交付启动核对。

| 类别                                 | 处理方式                                                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 原子写、冲突、定稿、确认、恢复、取消 | 保留有独立故障意义的检查，优先覆盖正确性                                                                           |
| 逐项状态映射                         | 并入现有作者状态呈现场景，删除单独镜像表的断言；陌生状态显示可识别的未知状态                                       |
| 方法与资产                           | 保留 manifest、真实可加载和产物完整性各自职责，去掉同一层重复目录遍历                                              |
| Python 文案断言                      | 本地维护项去掉纯编辑性锁定；原版随附两套短检查本轮保留整体入口，待方法资产同步时调整，不做筛选执行器或复制上游测试 |
| GUI                                  | 维持现有 6 个场景规模，将关键编辑场景的准备与前序长链解耦；失败时保留现场                                          |
| 真模型方法对比                       | 既有 2 个方案 × 18 项保留为专项评估，日常与普通发行不自动启动                                                      |
| 性能与截图                           | 复用现有脚本和截图，按本次风险检查，不建性能平台或新截图矩阵                                                       |

**工作要求**：

- 新增独立回归场景控制在两个高价值问题：目标切换一致性、默认模板污染。文章／方案错误、角色与编辑状态延伸已有场景；去掉低价值镜像项后，常驻测试场景总数不增加。不能把互不相关场景硬塞成超长用例来凑数量。
- CI 使用少量明确目录规则识别桌面、共同业务与兼容变化；仅 UI／说明修改不触发 DSH 完整 E2E。
- 桌面运行时完整套件选择一个主平台执行；确有平台差异的租约、路径与 Windows 启动保留专属验证，不在两个平台无差别重跑所有模型链。
- 核心检查摆脱“每次必须重建整套兼容发行包”的隐含依赖；同一 job 复用已准备资源，Windows 一次准备构建 NSIS 和 ZIP。
- 关键正确性 lint 规则启用 error；Hook 告警逐项确认原因，修真实依赖问题，不通过批量 disable 获取零告警。
- 架构守卫补齐自身承诺的 JSX/TSX 引用解析和图覆盖，或明确缩小输出声明。保留边界和循环检查，行数与文档数量仅作整理提示。
- CI 报告分别列出 GUI 交互和像素比较。CI 未执行像素比较时明确记为未执行；不用 ignoreSnapshots 后的绿色结果冒充视觉通过。

本轮场景数的比较口径固定为核心 Node 97、桌面运行时 9、GUI 6、DSH 运行时 1；两个既有兼容 E2E 入口另列，Python 的 215 个检查项另列。不同层的断言数不能混成一个数字来展示“减少测试”。

**完成条件**：列出检查的风险归属与删改理由；同一候选的核心／完整桌面运行时各执行一次；无关桌面变化不触发完整兼容链；一套 Windows 资源准备产生两种交付。重跑记录能说明对应新变化或失败原因。

### 第五批：核对、交付与文档收尾

- 最后候选代码冻结后做一次适用的组合核对；失败只修正并重跑受影响部分。
- 原生 Windows 构建，检查实际打包程序版本、preload、随包 Python、必要资产、更新清单和 SHA-256。
- 用户使用说明、当前状态和本版变更与实际交付同步。Actions 附件只保留当前版本验收、使用与校验材料，历史开发计划保留在仓库。
- 交付记录保留实现提交、构建 run 和后续文档提交。README 更新若晚于构建，明确源码归属，不为文档再次跑全套构建。
- GitHub 提交、构建产物、正式 Release 分开记录；正式发布按该次明确要求执行，不由版本号自动推断。

## 4. 验收标准

以下按实际结果填写，不以文件拆分数、代码缩减比例或测试总数代替质量。

| 验收项            | 必须满足                                                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC1 选择一致性    | A 慢 B 快、目录不可读、持久化失败后，前后端目标、访问状态、会话和持有租约对应正确；旧请求不能覆盖新状态                                                        |
| AC2 错误可见      | 坏文章保留可定位的不可读信息，正常文章可用；固定坏方案不静默替换；坏会话索引不自动变新会话                                                                     |
| AC3 依据真实性    | 缺失 failAsTemplate 不制造 shatter cue，同一正文不因系统补词多出诊断；真实显式 cue 行为保留，原卡文件不被批量改写                                              |
| AC4 角色一致性    | planner/editor 不再收到要求调用未注册委派工具的指令；角色权限与写手委派正常                                                                                    |
| AC5 写作保护      | 正文、段落、方法编辑在切换、取消目录、关闭和更新时规则一致；保存中受保护，冲突保留文本；头条 dirty 进入任务快照                                                |
| AC6 失败与类型    | 关键业务失败由边界转换一次，结果不靠“错误”前缀或 exec.failure 暗传；选定关键接口不再 Json=any                                                                  |
| AC7 输出与刷新    | 正常成功回执没有固定重复免责声明；有风险时给具体处理信息；任务结束一次逻辑刷新                                                                                 |
| AC8 测试成本      | 常驻场景总数不增加，独立新增最多两项；保留关键保护，每个删除项有重叠或低价值依据；GUI 编辑场景可独立运行                                                       |
| AC9 CI 真实性     | UI 改动不触发完整兼容 E2E；无差别跨平台重跑和同 job 重复准备消除；lint／守卫／像素结果与真实覆盖范围一致                                                       |
| AC10 原生交付     | 版本与源码提交匹配；Windows 实际包启动、Python、资产、更新清单与全部哈希通过；签名状态如实记录                                                                 |
| AC11 真实写作抽查 | 同一配置跑一本书的规划、两章接续与独立审读，再跑一篇头条；核对工具选择、保存版本、事实接续和无重复确认。作者阅读原稿与回报，记录新增回归，不因机械分数替代判断 |

AC11 使用现有客户端和方法，不新建验收平台。没有模型连接或作者评分时明确标记未执行，可交付候选构建，不能将整体验收写成全部通过。完整默认／原版方法对比在方法变更或产品比较任务中单独执行。

## 5. 最终验收报告要求

实施结束后只新增一份 `0.9.5-IMPLEMENTATION.md`，包含：

1. 实现提交、构建 run、版本及产物链接。
2. R1–R8 的完成状态、实际改动位置和有依据的未完成项。
3. AC1–AC11 的结果、证据来源；通过／失败／未执行分别记录。
4. 删除与保留的分支、说明、测试及构建步骤，各给出真实理由。
5. 相同场景的前后回执、请求／构建次数和实际可比较耗时。没有测量就不写性能百分比。
6. 真实写作与作者评价、签名、安装／更新的实际执行状态。

本计划当前交付物为需求、实施指导与验收标准。业务修改从第一批开始，按完成条件推进，不另外建立一套与代码并行维护的治理文件。
