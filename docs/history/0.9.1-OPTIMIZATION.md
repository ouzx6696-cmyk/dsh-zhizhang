# 0.9.1 优化意见：围绕作品持续协作

实施状态：主要建议已落到当前工作区，实际变化、核对结果和保留边界见 [0.9.1-IMPLEMENTATION.md](0.9.1-IMPLEMENTATION.md)。下文保留提出方案时的分析与范围。

日期：2026-10-31。本文依据当前工作区源码、0.9.0 迭代报告修订稿及整体源码审查形成，是下一版建议，不代表这些改动已经实现。0.9.0 目前仍是本地开发预览。

## 一、先明确项目要完成什么

writer-agent 面向需要持续创作的作者。作者可以从一个题材、资料、一篇已有稿件或一本写到一半的书开始，让 Agent 承担查阅材料、规划、起草、修改和编辑协作，并在写作台阅读结果、比较候选、作出决定。文章、章节和已确认的创作状态应在多次对话、重启和版本迭代之间持续存在。

两种模式的工作尺度不同，但共同目的很清楚：

| 模式 | 作者的主要工作 | 项目应提供的连续性 |
| --- | --- | --- |
| 今日头条 | 题材与资料 → 立项 → 标题与稿件 → 红笔与质检 → 交稿与作者采用 | 同一目录可管理多篇文章，每次任务明确文章及稿件版本 |
| 长篇 | 灵感、参考与规划 → 章纲 → 正文候选 → 采纳与审读 → 定稿 → 后续章节与修订 | 同一作品跨章节、跨会话推进，保留规划、已发生事实、候选、审读与修订之间的区别 |

方法方案是作者选择的工作材料；既有业务工具负责把操作落到作品；Pi 或 DSH 负责模型会话与执行；写作台负责阅读、比较和作者决定。这里不评价或调整写作方法内容。

独立客户端的意义，是作者不用配置 DSH 也能完成这些工作。换入口之后，原来由 DSH 承担的任务状态、对话呈现和上下文交接，需要有足够的替代。Electron 启动和模型接通只是这个目标的一部分。

据此，判断优化价值应看四件事：作者能否直接开始工作；Agent 是否知道正在处理哪份作品；结果是否落到正确位置并可回看；隔天回来能否接着写。

## 二、用这个视角重看上一份审查报告

0.9.0 审查对配置绑定、目录登记、会话恢复、作者确认和保存反馈的分析有价值。共享业务核心、使用 Pi SDK、保留文件格式的方向也应延续。

但报告仍主要从“新入口如何接通旧代码”展开，对产品使用过程的解释不够充分。有三处需要校准：

1. **会话与作品有关联，不等于任务已经知道作者当前所指。** 当前章节、文章、候选与读取版本没有完整进入自由对话。明确按钮已有目标文本，自由输入还缺这层连接。
2. **存在编辑任务，不等于作者已经拿到可用的审读结果。** SDK 运行结束、编辑最后一条文字、作品里的审读回报，是三个不同对象。界面应突出实际回报与稿件，而非仅显示运行结束。
3. **构建通过与部分接线修正，不足以作出完整可用判断。** 回查还发现头条按钮、历史关联和作者操作记录的具体遗漏，需要优先于一般性能优化处理。

因此，0.9.1 应定义为：补齐作者围绕作品连续工作的关键衔接，整理桌面端任务表达。暂时不扩大宿主范围或业务能力。

## 三、需要优先处理的源码问题

以下是静态调用关系能够支持的结论，未通过桌面运行复现；触发条件和影响分别列明。

### 1. 头条按钮仍依赖 DSH 会话登记

依据：`packages/workbench/src/client/toutiao/useToutiao.js:126` 仍以 `list.sessions[deliverRoot]` 决定能否投递；这些记录由头条接口经 `core/sessions.sessionFor` 取得。`packages/core/src/sessions.ts:76` 对没有 `exec.agent` 的桌面执行上下文直接返回，不登记 DSH 会话。

干净的独立客户端环境里，即使接口返回 `deliver: true`，界面仍可能以“没有会话”为由禁用新写、继续与编辑按钮。上一份报告中“投递能力已经接通”的结论不完整。

**建议：** 桌面按钮根据当前目录与桌面会话入口的实际能力启用，DSH 保留其原有会话条件。复用现有能力字段或一个局部宿主判断即可，不伪造 DSH 会话记录，不建设通用能力注册系统。

作者看到的结果应是：打开目录、配置模型后即可从写作台开始创作，不需要先在聊天框执行一次写作工具来激活按钮。

### 2. 首次建书的会话迁移条件过宽

依据：`apps/desktop/src/session.ts:352` 的 `bind` 根据“同根目录、原来没有 work、现在有 work”迁移会话；只检查目标是否已在内存中，没有判断作品是否刚由本次任务创建，也没有检查已有持久化会话入口。

因此，在存在根目录会话时选中已有作品，也可能被当成首次建书。若该作品的会话不在内存中，其 `current` 标记会被替换。这里主要是旧对话入口被改指，不能直接说旧 JSONL 文件已被删除。

**建议：** 用实际 `fanqie_project_create` 成功结果确认新作品，只有这类明确关系才延续根目录对话。普通浏览和选择已有作品只进入作品原会话。会话归属不根据页面恰好显示了什么来推断。

这应收敛在现有会话管理与建书结果处理处，不增设迁移框架或第二份聊天存储。

### 3. 作者操作通知尚未可靠成为历史

依据：`session.ts:426` 仅对内存中存在的会话调用 `sendCustomMessage`，并使用 `deliverAs: "nextTurn"`。固定版本 Pi SDK 的该分支把消息放入 `_pendingNextTurnMessages`，留待下一次用户提示消费，并非当场持久化。若在下一轮之前释放会话或退出，这条通知不会因此自动成为历史。

作品保存成功与否不受这条通知直接影响；缺失的是作者操作与后续对话之间的连续性。上一份报告对此的表述偏乐观。

**建议：** 已有关联会话时，使用 SDK 支持的、不触发模型回合的持久化自定义消息；运行中遵循 SDK 的消息落入时机。内容只记实际操作、对象与版本，不把整份接口结果反复序列化进对话。

没有关联会话时无需为了记一条提示启动模型。作品仍是事实来源，首次或后续任务重读相关状态即可。不要另做事件日志服务，也不要把聊天记录作为作品状态的唯一凭据。

### 4. 桌面提示与共享提示仍夹有两套宿主指令

依据：共享 `FANQIE_BRIEF` 和 `TOUTIAO_BRIEF` 包含 `subagent`、`writer_enable` 调用说明；长篇按钮文本还追加 `ENABLE_HINT_FANQIE`。桌面 `session.ts:289` 再追加“不调用 writer_enable、改用 writer_review”的说明。

当前做法让模型自行消解互相覆盖的宿主指令，效果依赖模型理解。原 0.9.0 迭代报告其实已经要求拆出宿主装配措辞，当前实现尚未完成。

**建议：** 保留业务总则与方法原文，仅把调用编辑、启用模式这些宿主说明留到 DSH/Pi 各自装配。共享按钮继续表达作者动作，启用提示由对应入口提供。只整理这几处字符串与装配函数，不重建提示词框架。

## 四、让会话真正服务于当前作品

### 5. 区分会话范围、页面位置和任务目标

当前 `Target` 只有模式、根目录和可选作品。长篇 hook 只同步根和作品；头条只同步根；自由发送只带文字和这个 `Target`。作者打开第十二章后说“修改本章”，模型并不一定知道页面正在看哪章。同一目录里的头条文章也有同样问题。

建议保留现有会话范围，同时补一份发送时捕获的少量上下文：

| 信息 | 生命周期 | 作用 |
| --- | --- | --- |
| 模式、数据根、作品 | 会话范围 | 决定恢复哪段对话、工具使用哪个项目 |
| 当前文章或章节、正文或候选、已加载版本 | 页面浏览位置 | 说明作者当前正在阅读什么，不因浏览新建永久会话 |
| 本次指令及发送时的对象 | 本次任务 | 保证作者切页后，进行中的工作仍处理原对象 |

这可以是几个字段组成的普通对象，不需要任务数据库。按钮与自由输入共用这份上下文，编辑任务也取得明确目标。章节切换不改变正在运行的任务，不按每章复制一个 Agent。

若页面有未保存修改，应清楚说明 Agent 读取的是已保存稿件；未经明确提交，不把作者的本地编辑缓冲区当作现行正文。

### 6. 长项目连续性建立在作品状态上

项目已经具备 `fanqie_product_map`、`fanqie_panel_snapshot`、`fanqie_chapter_brief`、正文读取和审读回报。Pi SDK 也已经提供会话持久化与上下文压缩。0.9.1 不需要另建长篇记忆系统。

建议把恢复或开始任务时的交接明确下来：

- 先让 Agent 得知当前作品、目标章节或文章、方法方案以及必要的状态变化。
- 写章时沿用章简报和正文读取；审读时沿用当前稿与既有回报；规划或拆书任务按其目标取材料，不强制全部经过写章流程。
- 对话压缩后仍从作品工具重读相关事实，不要求作者重新解释全书，也不把压缩摘要当作定稿事实。
- 作者切换方法方案后，后续任务明确使用当前方案；不为此创建按章、按角色的组合配置系统。

上面的交接只传少量位置与状态，正文按需通过原工具读取。不能每次发送都注入完整全书快照或重复粘贴方法库。

“开始新对话、保留作品”可以作为后续小增强，但不是修正上述问题的前置条件。现阶段先让现有会话正确恢复和推进。

## 五、把运行信息整理成作者能用的反馈

### 7. 突出任务结果与下一步

当前聊天主要逐条显示文本和工具结果，工具名直接作为进度文字。编辑任务最后返回的是最后一条助手文字；作品里其实已经有结构化审读回报、候选和质检状态。

建议从已有信息呈现三层内容：正在做什么；已产生什么；接下来需要作者决定什么。例如“正在审读第十二章”“已生成修订候选，可对照查看”“审读回报未通过，存在两处待处理问题”。提供跳到对应章节、候选或现有审读区域的入口即可，不新增成果数据库。

工具详情默认折叠，保留需要时查看的能力；仅含工具调用而没有正文的助手消息不显示为空白聊天气泡。流式文字与工具进度分开，避免“正在调用……”混入正文。

同时，忙闲状态不能只看 `isStreaming`。当前 `view` 正这样返回，但 SDK 的压缩、重试等阶段也可能尚未空闲。应以 SDK 完整生命周期和 `isIdle` 等已有状态决定运行与停止能力，不自己实现另一套调度状态机。

后台任务先提供一个轻量的运行提示，标明作品并可返回或停止。无需独立任务中心、持久队列或跨会话调度器。

### 8. 让正文与对话可以同时使用

当前 `.desktop-chat` 是固定在右侧、宽至 460px 的浮层，默认打开。它可能遮挡原三栏写作台右侧的审读与作者操作区域。源码能确定布局会重叠，具体影响程度仍需桌面观察。

建议宽窗口为对话留出实际布局空间，窄窗口保留可收起抽屉。沿用导航、Reader 和 Inspector，不重新设计编辑器。对话标题至少显示作品及本次任务对象，让作者知道这条指令会作用在哪里。

历史展示先限制初次传输和渲染的消息范围，旧消息按需展开，较大的工具结果折叠。这样可以降低界面负担，但并不等于 SDK 底层历史读取也已经变为增量；后者只有实际出现开销证据时再处理。暂不引入复杂虚拟列表或自定义聊天存储。

## 六、0.9.1 建议范围与实施顺序

| 优先级 | 工作 | 完成后的可见结果 |
| --- | --- | --- |
| P0 | 头条桌面投递条件与宿主提示装配 | 不依赖 DSH 登记即可工作，模型接到的调用说明一致 |
| P0 | 首次建书会话归属 | 新书延续原讨论，已有书保留原对话入口 |
| P0 | 作者操作记录与状态重读 | 采用、采纳、定稿后，后续对话基于真实已保存状态 |
| P0 | 统一发送时的任务对象 | 自由对话、按钮与编辑明确处理哪篇、哪章、哪个版本 |
| P1 | 复用作品工具完成恢复与任务交接 | 重启或压缩后继续工作，无需作者重述全书 |
| P1 | 任务反馈与编辑成果展示 | 能看见进度、稿件或回报，并知道待决定事项 |
| P1 | 对话布局与初始历史显示范围 | 可边读边交流，不被工具长输出淹没 |

实施应先把前四项作为同一条任务链处理，避免只修一个按钮或只加一个字段。随后统一整理恢复、反馈与布局，再构建和核对交付物。文档更新应同时纠正上一份报告中不完整的结论，不把本轮建议写成已实现能力。

现有工具工厂、门禁、业务文件、候选与审读服务继续复用；DSH 保持可装配，桌面打包保持独立。无需移动全部业务目录、给每个工具加宿主分支或抽象新的通用服务层。

多宿主插件、云同步、多编辑模型、自动发布、联网搜索供应商、独立工作进程和存储事务重写不纳入这次补丁优化。Windows 安装与真实模型的使用结论仍要明确记录；它们不应被一份新架构或更多测试数量替代。
