## 3. 需要纠正的事实和推论

### 3.1 revision 不能代表所有页面数据

当前 `chapterRevision` 只包含正文、章纲和位置。审读结果、章节状态和更新时间不参与该值。Inspector 又优先读取已加载正文的 meta，而不是只读快照中的状态。

本次新增 S1 复核：通过共同操作将同一段正文从 drafted 声明为 reviewed，正文和 revision 均不变，status 和 review 已变化。因此，“bodyKey 只用 revision，updatedAt 只作显示”若没有独立元数据更新，会继续显示旧审读状态。

修订要求：正文缓存按内容 revision 失效，元数据单独按可靠版本更新；两者尚未分离时，读取身份还须覆盖状态变化。正式回归同时包含正文改字、正文不变但审读变化、候选采纳及同项目切换，避免只修一个触发条件。

章节读接口可给 revision 与 bodyHash；候选应给自己的 bodyHash 与目标 targetRevision，不能把章节 revision 冒充候选内容版本。目录记录 revision 可以帮助合作写入，但外部直接修改章节文件不会同步更新目录，仍要明确发现机制与缓存失效范围。

### 3.2 消费服务与适配器不是同一个 prepareCall

指定 DSH 提交中的 `LlmAdapter.prepareCall(provider, model, signal?)` 位于 llm index.ts 约第 290 行；插件消费的 `LlmRuntime.prepareCall(config, signal?, configure?)` 位于约第 956 行。补充意见将两者写成同一签名，不能据此编写调用代码。

purpose 枚举不含 diagnostics，只能说明当前不能自造该分类，不能据此证明第三方正式调用记录路径一定不存在。原报告将它列为待验证项仍成立；Agent 路径减少自建调用记录的工作，但仍须确认工具结果实际记入对应会话，并核验提交来源。

### 3.3 当前侧栏没有第二套工作台

`src/client/index.jsx` 的 main 注册 App，sidebar.panellist 注册 SidebarIcon。当前源码不支持“侧栏和主页面各自挂载工作台，因此必然双重轮询”的判断。

多窗口和宿主重复挂载仍可能发生，需要实际验证。确有多消费者时可共享实例内的相同读取与请求预算，但当前作品选择、未保存编辑及确认目标必须隔离，不能把它们放进一个跨页面共享单例。

“一次只发一个请求”限定为后台自动读取的协调，不阻塞作者点击、取消、保存和对账。长轮询若以后采用，不能让一个等待 25 秒的 GET 挡住取消动作。

### 3.4 限量保存不等于停止扫描

要求精确 totalHits 时，应继续匹配并计数，只限制保存的具体命中；这限制分配，不减少必须完成的计数工作。若为时长预算提前退出，使用 scanComplete=false、已见数量或下界，不显示精确总数。

旧 lintStyle 的无参数行为与旧 strict 门禁计数保持兼容。新诊断接口可调用共同扫描内核取得有限明细与覆盖状态，不复制一份规则，也不必为了加字段破坏旧调用方的数组返回格式。

### 3.5 浏览器会话存储仍有保存语义

sessionStorage 通常跨刷新保留，结束的是浏览上下文会话，不是 DSH 的某个创作会话；浏览器或桌面恢复行为还可能影响其保留期限。因此只能说“会话级恢复缓存”，不能承诺每次创作会话结束就清空。

目前默认内存缓冲。若增加可选恢复，键至少绑定项目根标识、作品、章节或候选及源版本；恢复只进入待核对缓冲，须核对现行来源，并提供删除、过期清理和保存成功后清除。不能直接恢复为当前正文，也不能只按作品名避开同名跨项目冲突。

### 3.6 413 与任务容量都要有真正的边界

超限后停止保留正文，尽量返回结构化 413；排空请求仍需总时长与额外字节边界，不能等无限上传结束。连接已经中断时，客户端保留缓冲并报告传输失败，不把它解释成“服务器没有写入”。

任务条数与 TTL 可以替代对 JS 堆内存的精确统计，但前提是正文、模型原始输出、引文、原因、替换文本和报告总大小也有限制。“只有 120 条问题，所以内存自然有界”本身不成立。撤销栈同样不能只限步数而不管每步保存多少文本。

### 3.7 兼容门禁与认证观察不能代替实测

DSH 官方发行约定优先使用 `engines.dsh`，相应 peer 声明属于实际包依赖；应在真实目标宿主验证后填写确有依据的范围，不凭“rc 版本可能变化”随意收紧 peer。

gh auth status 可辅助诊断，但不独立证明某个目标仓库的 contents:write 或 uploads.github.com 的上传授权。此前 API 和 push 成功、上传端点 401 的事实仍应按实际结果保留，不归因为未经核实的权限缺失。

## 4. 更新后的版本与能力定义

0.19.1：单独修复已发行的正文／元数据失效，加入真实接口组合回归。修复不需要的诊断字段和候选 API 扩展留给 0.20.0，保持补丁范围清楚。

0.20.0：本地快速扫描、单段内标注、问题列表、整段编辑、差异预览、简单撤销、基线安全暂存和现有采纳完整可用。深度路径默认关闭，未验证时不显示可执行入口；可以提供准确命名的“生成诊断指令”，并将 Agent 结果提交作为一种独立能力。

后续：只有自动投递或宿主辅助调用完成验证，才提供真正的一键上下文深度扫描。模型未就绪不阻塞已完整验收的本地版本，但发行说明和能力页面必须明确仍未完成的目标。

## 5. 共同契约与测试调整

- `stageRevisionCandidate` 按 sourceKind 确定 captured 或 parent 策略，客户端传来的 basisPolicy 不能成为绕过依据核对的开关。
- 共同低层写入接收显式的已核对依据，旧 stage 入口可继续按原语义选择最近简报；不能一边要求旧行为不变，一边把所有旧调用的依据查询删除。
- 候选往返测试至少覆盖暂存、lint、采纳前后读取；中断恢复也必须保留新增来源和去重字段。
- 新旧渲染比较作者可见文本、段落与行内结构；保留有用兼容行为，对旧渲染的已知错误另立明确预期，不复制错误 HTML。
- 首版约 30 段人工评审记录每类的样本量、值得处理的条数与分歧。50% 是提醒复核的经验线，不是经过验证的自动判定阈值。
- 性能脚本与少量浏览器核对独立于默认 check；不因本轮评审增加长端到端流程。
