# 0.9.0 整体源码审查

后续校正：本报告保留为 0.9.0 历史记录；投递条件、建书会话归属及作者通知的遗漏和修正见 [0.9.1 实施记录](0.9.1-IMPLEMENTATION.md)。

日期：2026-10-31。对象为当前工作区的 0.9.0 独立客户端与共用业务代码；不是对已发布版本的验收结论。

## 整体判断

这个项目的主体是有持续状态的写作工作流：方法方案提供材料，主写手调用工具推进文章或长篇，候选与审读产生可供作者判断的结果，作者采用或定稿，作品文件保存事实，对话负责协作。桌面聊天框只是其中一个入口。

沿着这个结构审查，现有业务核心可以继续复用。0.9.0 的主要问题集中在新入口如何把目录、作品、会话、编辑任务和作者操作关联起来。单个接口能够返回、工具能够构造，并不说明这些关系始终一致。本轮据此修正了具体衔接，没有重写创作方法或另建一套业务引擎。

当前可以交付为开发预览；仍不能宣称 Windows 实机和真实模型的完整创作流程已经验证。

## 实际结构与职责

| 部分 | 当前职责 | 审查判断 |
| --- | --- | --- |
| `apps/desktop/src/main.ts` | Electron 生命周期、目录选择、模型设置、原生作者确认、IPC 操作分派 | 应统一入口状态，不承担第二套写作规则 |
| `apps/desktop/src/session.ts` | Pi 主会话与编辑任务、工具绑定、事件、停止、历史 | 每个任务必须绑定明确目录和作品，不能跟随界面读请求漂移 |
| `packages/toutiao`、`packages/fanqie` | 既有工具、门禁、文章与长篇存储、候选和审读 | 继续作为业务事实来源 |
| `packages/workbench` | 共享 React 写作台与操作上下文 | HTTP 和 IPC 复用同一业务处理，传输方式不进入业务规则 |
| `packages/core`、`packages/host` | 文件、Python、方法方案、执行上下文与宿主适配 | 显式接受桌面上下文，保留 DSH 适配 |
| `scripts` | 共享资产准备、DSH 包、桌面资源与 Python 打包 | 同一来源生成两种入口的资源，避免维护两份方法资产 |

桌面端由 Renderer 经 Preload 调用 Main；Main 直接调用共用业务操作或 Pi 会话，不启动本地 HTTP 服务。DSH 仍使用原宿主接入与 HTTP 写作台。

## 按完整使用过程发现的问题与修正

### 1. 打开目录与选择作品

原实现会在一般读取请求中修改当前对话目标。页面刷新、旧请求返回和作者主动选择混在一起，可能把下一条消息或停止请求送到另一作品。

现在读取不改变目标；作品选择通过明确的 `writer:select` 完成。界面由已读到的项目、作品状态发布选择，Main 保存规范化的目录与作品标识。异步选择和历史返回会检查是否仍为当前选择。取消目录选择不改变会话。

沿此链路进一步发现：长篇目录通过 `ensureStorage(null, ...)` 创建后，原先没有明确登记项目，界面显示的可能只是项目列表临时补出的条目。现在目录选择等待现有项目登记完成，并使项目摘要缓存失效。已有项目的自定义 `worksRoot` 同时用于目录选择、页面操作和 Pi 工具，避免界面看到一套作品而 Agent 使用另一套。

空项目也同步选择，因此从已有作品切到空目录时，对话不会继续指向原作品。目录切换还会重置不适用于新目录的界面偏好。

对应：`main.ts` 的 `selectTarget/request`，`session.ts` 的 `create`，长篇 `work-store.ts` 的 `rememberProject`，两种模式的界面 hook。

### 2. 从空项目开第一本书

对话最初只有数据根，建书后才出现作品标识。若直接按新标识创建会话，就会把同一创作过程拆成两个会话，影响历史、流式显示和停止。

现在根目录会话只在创建首本书且目标尚无内存会话时，绑定到作品会话；继续使用原 Pi 历史文件，并移除旧标记，避免两个入口以后同时打开同一文件。工具与事件使用更新后的目标。已有作品之间仍各自保留会话。

对应：`session.ts` 的 `key/bind`。

### 3. 恢复历史与切回任务

查看历史原先会顺带准备模型会话，导致只想看旧对话也需要有效模型配置。界面切换后，历史、忙闲状态与正在输出的文本也可能不同步。

现在 `view` 独立读取持久化历史；已有运行会话则返回其当前消息、输出和状态。查看历史无需启动模型。界面丢弃已经过时的返回结果；离开的闲置会话释放内存，持久化文件继续保留。

对应：`session.ts` 的 `view/release`，`client.jsx` 的 `showTarget`。

### 4. 发送、报错与停止

原实现可能在会话尚未准备成功时就返回发送成功，输入先被清掉；SDK 错误也可能只留下空的助手消息。

现在先完成会话准备再接受发送，准备失败保留输入。异步错误带原任务目标，避免显示到另一作品；助手错误进入可见提示。编辑任务的错误或中止会回传主写手，不作为正常结论。停止覆盖主会话及其编辑任务，并处理编辑准备期间已经取消的情况。

停止只中止后续执行，不撤销已经完成的作品保存，这与现有文件工作流一致。

对应：`main.ts` 的 `writer:send`，`session.ts` 的 `writer_review/stop`，`client.jsx` 的事件处理。

### 5. 编辑与作者决定

编辑继续是独立 Pi 会话，沿用既有编辑工具限制与门禁；不增加通用文件写入或命令执行工具。长篇配置通过已有的配置上下文绑定，避免并行会话共用可变配置。

作者确认原先由额外的确认 ID、Map、IPC 回传和 React 弹窗协调，多任务确认可能覆盖同一弹窗。现在使用 Electron 原生确认对话框，按顺序显示，并跟随任务取消。现有门禁判断及确认消费逻辑不变。

页面的采用、采纳、审读、定稿仍调用既有业务操作，并把结果通知关联会话。操作已经保存但通知失败时，保留保存成功的结果，另行提示通知错误，避免作者误以为需要重复保存。

对应：`main.ts` 的 `confirm/request`，`session.ts` 的工具执行包装与 `notify`。

### 6. 写作台与 DSH 共存

桌面不再通过伪造 DSH 消息投递能力来启用按钮；头条操作显式接受投递能力判断，DSH 默认行为保留。新文章使用当前选择目录，而非最近 DSH 会话或目录列表第一项。

IPC 读取结束后检查取消状态，避免旧读取继续更新界面；头条界面卸载时也清理未完成读取。桌面通过任务与操作事件刷新，保留 DSH 原有刷新机制。

公共 `RouteContext` 只暴露业务需要的 URL、方法、正文与响应函数。没有为桌面伪造 Node HTTP 流，也没有新增服务进程或监听端口。

对应：头条 `workbench/api.ts`，共用 `server.ts` 与 `client/shared/api.js`，两种模式的界面 hook。

### 7. 配置、资源与启动

模型设置先解析候选值和加密内容，再停止现有会话、保存并切换配置。写入失败时不提前替换内存中的模型连接。界面说明保存连接会停止正在运行的任务。

最近长篇目录恢复失败时显示原因，仍允许重新选择目录。其他导致启动失败的配置错误仍由启动错误框报告，没有扩展成一套配置修复系统。

方法、规则脚本和默认方案由共享资源脚本准备；Windows 包使用固定来源且校验过的 CPython。Python 执行器支持带空格的绝对可执行文件路径。桌面应用状态使用 Electron userData，作品与用户方法仍在所选目录；DSH 默认状态位置保留。

## 效率与复杂度判断

当前版本不需要引入任务数据库、额外后端、通用插件框架或跨宿主消息总线。Pi 保存会话，既有存储保存作品，桌面层负责关联即可。业务规则没有再复制一遍，编辑继续复用现有工具限制，这两个方向是合理的。

本轮删掉了桌面自建确认往返和伪消息投递适配，减少无效的会话初始化，并释放离开的闲置会话。它们是从代码路径可以说明的简化，不等同于已测得的性能提升。

仍有两个明确的使用边界：

- 对话历史目前整体传回并渲染。极长会话的打开与显示成本尚未量化；本轮没有为此增加分页系统。
- 切到其他作品后，原任务可以继续运行；当前没有独立的后台任务总览，需要切回对应作品查看与停止。没有将其扩展为多任务调度平台。

独立版与 DSH 同时写同一作品不属于本轮支持的使用方式。

## 本轮核对范围与剩余事项

本轮以源码、调用关系和实际配置路径为依据，没有新增测试，也没有运行单元测试、DSH 集成测试或端到端测试。修改后的公共与桌面 TypeScript、生产构建、两种包的生成用于确认代码能构建及资源能交付，不能证明交互与创作效果。

本轮完成：上述衔接问题修正、桌面生产构建、DSH tgz 与 Windows x64 ZIP 重新生成、ZIP 完整性及关键资源核对。初版交付时已完成的架构守卫与运行时下载校验见 [交付记录](0.9.0-IMPLEMENTATION.md)。
