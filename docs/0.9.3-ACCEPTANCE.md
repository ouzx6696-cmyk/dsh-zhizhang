# 0.9.3 验收规范

本文件规定怎样证明[需求计划](PLAN-0.9.3.md)已实现。实际执行结果填写到[验收报告](0.9.3-ACCEPTANCE-REPORT.md)。下列用例均是本版要求，不代表已执行或已通过。

## 1. 结论与证据规则

验收状态统一为：通过、失败、受阻、未执行、不适用。受阻说明已经确认的外部条件；尚未尝试不叫受阻。不适用仅用于事先定义的可选条件，例如未提供证书时的签名校验，不能用于删除本版必需功能。

每条执行证据包含：被测 SHA、工作区差异、操作系统和工具版本、用例编号、前置数据、命令／操作、开始结束时间、实际结果、退出码、产物或截图位置、执行人。性能证据另保存原始样本、统计口径和环境。模型 Key 不进入记录；真实稿件保存在本地验收输出，不默认公开上传。

通过要求观察到业务结果；PID、端口、回合结束、测试退出 0 或模型声称完成都不能单独代表功能通过。跳过、零测试、fixture 构造质检元数据不能冒充真实写作通过。

同一个执行目录只对应同一提交和一次运行。工程证据建议放在 `outputs/acceptance-0.9.3/<run-id>/`；真实模型产物放在 `acceptance-results/0.9.3/<run-id>/`。这些路径已被忽略；报告列出可定位的本地路径或 CI 链接和产物摘要，不将凭据或作者作品提交到 Git。

## 4. 长历史性能验收口径（A22）

以下数字是本版拟采用的可用性要求，不是现有性能实测结果。M0 固定环境和样本后使用同一口径，不在看到结果后临时放宽指标。

- 参考设备：Windows 11 x64、至少 4 个逻辑 CPU、8 GiB RAM、SSD；记录具体 CPU、内存、缩放、应用模式和提交。1440×900 窗口。条件不足时给出实际测量与限制，不能冒充参考设备通过。
- 样本：由 PI 支持的会话接口生成至少 10,000 个有效历史 entry、约 20 MiB 的实际 JSONL，含用户消息、长工具结果、作者通知和历史分支。保留样本 hash 和生成方式。初次显示 80 条；两个作品各有独立会话。
- 冷读取：新应用进程、无应用内历史缓存，选择作品到首批消息可用，5 次均不超过 2 秒；系统页缓存状态需记录，不冒称磁盘完全冷启动。应用启动及模型网络时间另列。
- 热读取：同进程对两个作品切换／请求首批历史 30 次，端到端 P95 不超过 500 ms；统计采用排序后 `ceil(0.95×n)` 项。
- 交互：历史加载时本地输入／切换按钮不出现超过 1 秒的持续无响应；使用自动化交互记录，不只凭截图判断。
- 内存：预热后进行 20 轮 A↔B 切换及历史加载，以同一进程树口径测量，静置后 RSS 增量不超过 50 MiB；记录采样时机，不以重启进程或清空历史达标。
- 正确性：A21 必须先通过；API 省略内容、错误复用缓存或丢消息即失败，即使性能数字达标。

需调整要求时先记录硬件或产品依据，更新计划和规范，再测新基线；同时保留旧结果。Linux 结果可辅助定位，不代替 Windows 产品性能结论。

## 5. 真实写作验收（A28）

沿用[真实模型验收说明](ACCEPTANCE.md)及现有脚本，每套方法固定：资讯线长图文 3 篇、故事线长图文 2 篇、微头条 2 篇，长篇规划 1 项＋同一本书 10 章；共 18 项任务，两套共 36 项。第六章前新对话。任务 ID 和产物对应关系不得变化或重复补数。

| 指标 | 通过条件 |
|---|---|
| 完整性 | 两套任务各 18 项均有对应实际产物；每套 7 篇文章、同书 10 章及其章纲，不同任务不重复计数 |
| 头条质检 | 每套首次过线率 ≥60%，两次内 ≥90%；固定分母为 7。过线同时满足 ≥84、零 fail、无硬闸，稿件和立项卡指纹有效 |
| 独立编辑 | 每套 10 份对应当前正文的独立编辑完整回读回报；编辑通过率 ≥70%，平均硬伤数 ≤1，固定通过率分母为 10 |
| 连续性 | 每套十章连续性错误 ≤2；作者确认第六章新对话后无需重述设定即可接续 |
| 人工评分 | 每套 17 份有效评分，可读性和像人写程度均为 1～5；默认综合均分不低于原版。汇总不替代作者最终审稿 |
| 用量和费用 | 任务耗时和可得 token 留存，实际费用及币种由真实账单核对；缺失保持 null，不能填 0 冒充免费 |
| 作者权限 | 自动运行停在候选／待决定阶段，不代作者定稿和标记已交稿 |

此处沿用既有 E 集建议线作为本版效果验收线；质量判断仍需作者抽查，不因一轮结果自动改写方法库。缺少模型、来源或评分时明确未完成，工程工作可继续。

建议执行方式（在仓库根目录，使用本轮全新的输出目录）：

```bash
writer_acceptance_dir=acceptance-results/0.9.3/run-001
npm run acceptance:prepare -- --output "$writer_acceptance_dir"
# 编辑生成的配置，只填写非秘密模型元数据、apiKeyEnv 和新闻链接。
# 凭据在安全环境配置中提供，不写入命令参数或报告。
npm run acceptance:run -- --config "$writer_acceptance_dir/acceptance-config.example.json" --output "$writer_acceptance_dir"
# 作者完成评分和账单后，仅重新汇总，不再次调用模型：
node scripts/acceptance.mjs --summarize --output "$writer_acceptance_dir"
```

运行前把示例 run-001 改为本轮未使用的新目录。脚本汇总退出 0 只表示完成汇总；还必须核对 metrics、缺项、作者项和 COMPARISON 的实际结论。

## 6. 工程和交付命令

根目录工作流：

```bash
npm ci
npm test
npm run test:desktop
npm run desktop:build
npm run test:desktop:ui
npm run pack
```

共享业务变化时，使用已安装的 `WRITER_DSH_RUNTIME` 执行既有 `npm run test:dsh`、`npm run test:e2e`、`npm run test:e2e:fanqie`，核对确有执行而非因缺运行时跳过。`npm run test:all` 当前不包含桌面和真实模型，不能单独代表本版完整验收。

Windows 原生交付继续使用 `npm run desktop:pack`、`npm run desktop:portable`，必要时先构建一次再调用对应 workspace 的 pack 避免重复构建。核对 NSIS／ZIP、Python／字体／许可证、校验清单以及版本一致；Linux 构建不能代替 Windows 包与安装行为。检查脚本实际上传／发布设置，验收本身不执行正式发布。

日志重定向或 tee 必须保留原命令退出码；记录测试 passed／failed／skipped／未执行的实际数量及目标。CI 和包必须对应同一个被测 SHA；代码变更后的受影响证据需重跑。

## 7. 三项独立完成结论

| 结论 | 必须具备的证据 | 不足时的写法 |
|---|---|---|
| 工程验收 | A01～A26 及 A27 工程子项的功能、性能、类型、构建、真实 Electron 和所需存量回归通过；A27 实机子项另记发行条件 | 明确失败／受阻／未执行项，不写“全绿” |
| 产品效果验收 | A28 自动条件及人工项完整通过，作者核对权限、产物和连续性 | 工程通过，实际写作效果尚未验收／未达线 |
| 发行条件 | 同提交 Windows 包校验、实际设备安装和旧数据检查完成；签名和跨已发布版本更新状态明确 | 可保留开发候选，但未满足的发行条件不得写成已验证 |

实际设备安装属于必需交付子项；签名在提供证书后验证，未提供时明确未签名且不声称通过签名。跨已发布版本更新有可测试版本对才执行，条件不具备时明确未验证、不得宣传该功能已经验收。开发、验收、产物准备和正式发布是独立事实。

任何作者数据损坏、未授权敏感写入、跨作品串写、确认错误版本或丢失已保存内容的缺陷均阻止工程验收。其他必需项失败同样不计整体通过；修复后复测对应项并检查关联项，不能修改预期掩盖失败。
