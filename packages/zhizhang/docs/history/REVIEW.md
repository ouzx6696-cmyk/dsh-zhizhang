# 全局梳理 · 2026-10-27

> 历史评估：描述 0.17.0 基线及当时的问题，不是当前实现声明。0.18.0 实施与验证以 [IMPLEMENTATION.md](IMPLEMENTATION.md) 为准。

织章的主线是：参考书原文与事实 → 可迁移的参考卡 → 作者采纳的规划 → 章节写作、扫描与采纳 → 续写或汇编。代码负责文件、状态、确认与恢复，AI 提交创作内容；机械检查不能证明阅读深度或创作质量。

## 当前实现地图

| 环节 | 入口与实现 | 核对结果 |
| --- | --- | --- |
| 宿主接入 | `src/index.ts`、`src/lib/bootstrap.ts` | 默认只挂启用入口，启用后注册工具；发行代码由同一套测试加载 |
| 拆书 | `src/tools/library.ts`、`src/tools/analysis.ts`、`src/lib/ports/analysis/*` | 计划、事实、阅读申报与来源校验各有明确含义；全量阅读须确认 |
| 参考卡 | `src/lib/ports/library.ts` | 双轴分工保留；v2 卡接受前复核原文，旧卡兼容但不补造阅读证据 |
| 规划 | `src/lib/ports/inspiration.ts`、`src/lib/domain/planning.ts` | 根基、全书、卷、幕和章纲显式应用；历史可从已采纳候选查看 |
| 写作 | `src/tools/methods.ts`、`src/lib/services/accept.ts`、`src/lib/storage/chapters.ts` | 简报承接前章，扫描凭据绑定正文；采纳与定稿分开 |
| 数据保护 | `src/lib/storage/*-journal.ts`、`process-lock.ts` | 主要多文件写入有冲突检查及恢复；参与锁的进程串行写入 |
| 作者面板 | `src/lib/http-api.ts`、`src/client/client.js` | 正文按需读取，采纳需确认；规划显示摘要，完整编辑经工具进行 |
| 交付与备份 | `assembleManuscript`、`scripts/backup.mjs` | 汇编与离线备份；备份有完整性校验，不自动恢复或迁移 |
| 校验 | `npm run check` | 静态护栏、构建及四个测试文件，无独立长流程或烟测脚本 |

## 本轮发现并修正

1. 汇编原先吞掉章节读取错误并跳过，可能将不完整内容写成成稿。现在持作品锁读取，筛选后的章节缺失或损坏会终止，保留旧成稿。
2. 汇编输出原先可指向存储根内的作品文件。现在限定在 `manuscripts` 中，并检查实际输出目录，拒绝指向源资产目录的链接。
3. 人物分析的错误形状会被读成空数组，部分分析或计划错误在面板中被隐藏。现在明确报错，由面板上层显示不可读状态。
4. 章纲透镜缓存只比较修改时间和大小。现在同时检查文件变更时间及 inode，并检查待恢复状态。
5. 数据说明仍宣称库只有进程内锁；版本注释仍提到已移除烟测；变更文档有不存在的归档链接。已修正这些残留。

## 需要明确保留的边界

- 资源锁只协调配合的进程，外部编辑不会被锁阻止；恢复的哈希核对不能构成对任意外部写入的原子保护。遗留锁不会只凭超时自动删除。
- 当前没有断电持久性、Windows 文件系统及真实 DSH 宿主的验收证据。
- 小说状态仍由根基、前章正文和短摘要组成，不是完整的故事事实数据库；修订旧章后仍需作者核对相应状态。
- 规划可以在工具中查看、修改并重新采纳；面板提供阅读和采纳，尚无完整的可视化规划编辑器。
- 旧资产采取兼容读取，不自动批量迁移；旧版本无恢复记录的中断、恢复记录损坏及冲突需人工核对。

## 后续维护优先级

- **优先维护恢复协议**：目前有八个恢复模块，共享概念但各自重复格式验证、文件分类与清理逻辑，模块间也有相互引用。后续可提取公共执行机制，保留各自的目标文件白名单与旧记录兼容；本轮未进行格式迁移。
- **继续收拢模块职责**：`store.ts` 仍同时承载资产存储、项目索引、面板汇总和汇编；HTTP 与库端口也较大。下一次按业务边界逐块拆分，避免再次扩张外观层。
- **完善异常数据识别**：现有校验覆盖主要文件形状，尚未逐项严格验证所有旧章节目录项和历史字段；不能把当前测试通过解释为任意损坏资产均可自动修复。
- **目标环境验收**：需要真实 DSH 和 Windows 环境后，验证宿主挂载、权限、路径与文件链接行为。
